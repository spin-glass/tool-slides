# design-doc — 設計書と、決めたことを確かめるスライドを同じ主張の表から作る

設計書の改稿と意思決定者向けスライドは別々に書かない。原資料 → 主張の表（根拠と状態を確かめた共通メモ）→ 設計書／確認型スライド → 原文との照合、の順に作る。
スライドの作法（聴衆・行動・時間、ゴーストデッキ承認、lint、全枚スクショ）は `slides` スキルに従い、ここではその上に乗せる手順と型だけを書く。

## 成果物と置き場所（1案件＝1フォルダ `<yyyy-mm-dd>-<kebab-name>/`）

| 成果物 | ファイル | 雛形 | 検査 |
|---|---|---|---|
| 主張の表 | `claims.csv` | `templates/claims.csv` | `scripts/claims.py` |
| 設計書（組み替え） | `design/<文書名>.md` | `templates/design_doc.md` | `scripts/check_doc.py`（`--render` で Mermaid を PNG にして目視） |
| 確認型スライド | `index.qmd` | tool-slides の `decks/_template_confirm/index.qmd` | slides の `lint_slides.py`（`kind: confirm` の規則）と `render_check.sh` |

**フォルダを置く場所は `slides` スキルの「デッキの置き場と、スキルの呼び方」に従う。** tool-slides の中なら `decks/` の下、他のプロジェクトで作業しているならそのプロジェクトか個人の置き場に置き、スクリプトは `python3 ~/.claude/skills/design-doc/scripts/...` で呼ぶ。設計書の原文が社内の資料なら、公開リポジトリには置かない。

見本: tool-slides の `decks/2026-10-01-invoice-ocr-confirm/`（架空の題材: 請求書を OCR で読み取る方式への切替。確認型5枚＋付録3枚、運用・移行設計の組み替え案、主張19件）。

## 数値ルール（lint・check_doc が機械的に検査する。slides の表に足す分）

| 対象 | 目標 | block |
|---|---|---|
| 確認点 `::: {.check}`（kind: confirm の本編） | 1枚に1つ、全角40字以内、1行 | 0個・2個以上・40字超 |
| 確認型のタイトル | 決めたことを「〜します」で言い切る。2行まで | 全角56字超（40px で1行約28字） |
| まだ決めていない値 `[要確認]{.tbd}` | 1枚目の `::: {.undecided}`（まだ決めていない点の一覧）に対応 | 一覧が無いのに `.tbd` がある |
| 主張ID `<!-- claims: C1,C2 -->` | `claims.csv` の id | 無い id／未決の主張を載せた枚が未決と分かる形でない |
| `claims.csv` | 列9つ・状態7つ（`references/claims.md`） | 列・状態・target の誤り、事実・決定に evidence が無い |
| 設計書の章参照（§3.4・3.4節・第3章） | 本文にある章 | 無い章（他の文書は「基本設計 §5.1」「原文 §2」と文書名をすぐ前に付ける） |
| Mermaid | 1行目が図の種類（flowchart / gantt / …） | 種類でない・描画エラー |
| 設計書の placeholder | 0（`[要確認]` は未決の印として可） | TODO・TBD・XXX・〇〇 |
| 中身の無い段落（削除候補） | 0 | 数字・主張ID・§・`コード`・「固有の語」・`[要確認]` のどれも無く、一般論・前置き・ヘッジだけの段落か箇条書き |
| 繰り返し | 0 | 文書内で同じ文（全角20字以上）が2回、同じフォルダの別の設計書と同じ文（全角30字以上） |
| 読む字数（文章＋表のセル＋図のラベル） | 原文の80%以下（「冗長」と言われたとき） | —（原文より多いと warning） |
| 同じ主張を書く場所 | 正本の章と §1 の要点の2か所まで | —（同じ主張IDが3か所以上で warning） |

warning（止めないが直す）: 章（`##`）の見出しの直後に図（Mermaid・表・画像）が無い、章番号（`## 3.` / `### 3.1`）のない見出し、確認型の本編の枚に `claims` が無い、1段落が全角200字超・1章の文章が1000字超、一般論・前置き・ヘッジが1段落に2つ以上・文章1000字あたり3つ超、バズワード、表のセルが一般論だけ・表どうしで同じセル、同じ主張IDが3か所以上（再掲）、読む字数が原文（`design/_source/<同じ名前>.md`）より多い、ひし形のラベルの1行が10字超、設計書に載せるはずの主張（`claims.csv` の target が doc / both）が本文に出てこない（削りすぎ）、未決・提案に決める担当が無い（claims.py）。
辞書は `references/ng_doc.md`（一般論・前置き）と slides の `references/ng_words.md`（ヘッジ・バズワード）。閾値は `scripts/verbosity.py` の `LIMITS`（初期値）。

このスキルの frontmatter の `hooks` は Claude Code だけが読む（プロジェクトの `.claude/skills/` → `~/.claude/skills/` の順に探し、どちらも無ければ何もしない）。
Devin CLI はスキルの frontmatter から hook を読まないため、ゲートはリポジトリの `.devin/hooks.v1.json` に置く。
他のリポジトリで同じゲートを使うなら、そのリポジトリに `.devin/hooks.v1.json` を置き、`CLAUDE_PROJECT_DIR="$DEVIN_PROJECT_DIR" python3 "$HOME/.claude/skills/design-doc/scripts/check_doc.py" --hook` と `CLAUDE_PROJECT_DIR="$DEVIN_PROJECT_DIR" python3 "$HOME/.claude/skills/slides/scripts/lint_slides.py" --hook` を Stop に登録する。

## フェーズ0: 原資料を主張の表にする（生成禁止ゲート）

スライドも作るときは slides のフェーズ1（聴衆・行動・持ち時間）に加えて、設計書だけのときは「読む人」と「この文書で決めること」に加えて、次が揃うまで書かない。

本人に尋ねられないとき（「任せる」と言われた、試験など）は、スキルの推奨で仮に決めて進める。仮に決めたことは主張の表の note に「仮」と書き（担当は「総務課長（仮）」の形）、報告の冒頭に一覧で出す。決め方まで書けない未決は、決め方を「本人に確認」とする。

1. **原資料の所在と版**を確かめる（Notion・添付・URL・行数）。読めない原文を要約や記憶で代用しない。
2. **主張の表 `claims.csv`** を作る。1行＝1主張。列と状態の意味は `references/claims.md`。
   - 原文の箇所（文書名・§・行）を必ず書く。原文に無い主張は 提案 か 未決。
   - 状態は7つ（事実／参考値／方針／想定／提案／決定／未決）。原文に「こうする」と書いてあるだけなら 方針、見積りや仮の期間は 想定、「約1%（再集計する）」のような再測定前の数は 参考値。実績・確約と書かない。
   - 矛盾する記述は両方を note に残す。生成器が勝手に片方を正解にしない。
   - 無い費用・日程・性能は 未決 にして決める担当（owner）を書く。補完して断定しない。
3. `python3 .claude/skills/design-doc/scripts/claims.py <案件>/claims.csv`（tool-slides の外なら `python3 ~/.claude/skills/design-doc/scripts/claims.py ...`）で検査し、未決の一覧を本人に見せる。

## フェーズ1: 整合と不足を確かめ、先に決める項目を出す

原文を通して読み、次の6種類のずれを探す（最初に適用した設計書4文書では6種類すべてが見つかった）。

1. 何から何へ変えるか（現行と変更後）、何が対象かが複数通りに読める
2. 用語の意味が混在する（例:「保留」＝文字が読めない／確信度が低い／対象外の書類の疑い）
3. 判定の規則が文書間で違う（例: 項目ごとに閾値と比べる／書類の全項目が閾値以上なら採用）
4. 合格条件と警報の条件が別の指標・別の数値で、互いの関係が書かれていない
5. 変更・復旧の単位に、最も頻繁に変える設定（閾値）が入っていない
6. 組織名が文書間で違い、対応表が無い

指摘は4つに分ける: **編集で直せる／別文書で補える／設計判断が必要／根拠を実測する必要がある**。一般論を足して設計済みに見せない。
設計判断が必要なものは、推奨（根拠つき）と残る確認を本人に1回でまとめて尋ねる。推奨は 提案 として表に入れ、本人が採ったら 決定 に変える（決めた人と日付を evidence に）。
意思決定者に上げるのは、業務側にしか決められないこと（例: 人の確認に回してよい割合の上限）だけ。担当者間で片付く設計の整理（規則の統一、本番の設定の単位、組織名）は設計書の中で片付け、スライドの本編にしない。

## フェーズ2: 設計書を組み替える（`design/<文書名>.md`）

規約と理由は `references/design_doc_guide.md`。

### 2.1 先に削る（組み替えの前に）

冗長さは要約では直らない。条件・例外・担当を言い換えて短くすると、そこが落ちる。縮めるのは「段落を丸ごと削る」と「繰り返しを1か所にまとめる」で行い、残す段落は主張の表と対応させる。

1. 原文を `decks/<name>/design/_source/<文書名>.md` に置く（Markdown にする）。`_source/` は .gitignore 済みで、検査の対象外。**このリポジトリは公開されているので、仕事の原文はコミットしない。**
2. `python3 .claude/skills/design-doc/scripts/check_doc.py --candidates decks/<name>/design/_source/<文書名>.md` で、削除候補（中身の語が無く一般論・前置き・ヘッジだけの段落）、一般論の多い段落、同じ文の繰り返し、原文の参照の誤り（存在しない章）を一覧にする。`--paragraphs` は全段落の作業表（行・中身の語の有無・一般論の語）を出す。
3. 原文の段落を、`--paragraphs` の表で全部、次の4つに分ける。`--candidates` の一覧は出発点で、候補でも扱いが必要な話題（障害時の回復、セキュリティ）は「未決にする」へ回す。
   - **残す**: 決定・条件・担当・数値・手順・例外・期限のどれかを含む → 主張の表の1行にする。ヘッジに包まれた判断（「導入が望ましいと考えられる」）は、ヘッジを外した1文にし、決めた人と日付が無ければ 方針 にする
   - **1か所にまとめる**: 同じ内容の繰り返し → 正本の章だけに書き、ほかは「§4.2 を参照」にする
   - **削る**: 一般論・心構え（「継続的に改善することが重要である」）、文書についての前置き（「本章では〜を説明する」）、言い訳・ヘッジ、どの文書にも書ける AI・運用の一般論の章
   - **未決にする**: 必要そうだが中身が無い（「セキュリティに万全を期す」）、または原文の中で矛盾する（0.75 と 0.8）→ 主張の表に 未決 で入れ、決める担当を書く。矛盾は両方の値を正本の章の1か所に並べる。文を残して完成に見せない
4. 削った段落の一覧（原文の行・先頭の語・4分類・理由）は本人への報告に入れる。設計書の付録には書かない。原文が仕事の資料なら、一覧もリポジトリに入れない。
5. 書き終えたら `check_doc.py --original decks/<name>/design/_source/<文書名>.md decks/<name>/design/<文書名>.md` で、原文と書き直しの**読む字数**（文章＋表のセル＋図のラベル）・段落数・一般論の数を比べて報告に書く。「冗長」と言われたときの目安は原文の80%以下。原文より多ければ check_doc が `read-growth` を出す。再掲（`restated`）・付録の説明・足した未決を見直し、それでも増えるなら理由を報告に書く。block（削除候補・繰り返し）を0にし、`claims-unused`（載せるはずの主張が本文に無い）が出たら削りすぎを疑う。

### 2.2 組み替える

要点:

- 冒頭1ページは「この文書で決めること／読む人／関連文書／原文／状態」の表。複数文書で同じ「位置づけと読み方」を使い回さない。
- 章の順: 要点と判断事項 → 現行と変更後の全体像 → 日常の流れ → 判断基準と例外・変更（情報の取り扱いなどの非機能もここ）→ 計画 → 体制と作業量 → 付録。各章は、具体的な質問に答える見出し → 結論 → 図か表 → 詳細。原文に無い話題の章は作らない。
- **同じ事実を書くのは2か所まで。** 条件・数値・担当の全文を書くのは正本の章だけ。§1 の要点は1行と正本への参照（「→ §4.2」）にし、数値を再掲しない。対照表・流れの表・計画の表で同じ条件を書き直さず「§4.2 の3条件」と参照する。主張ID（C1）は正本の章で1回だけ添える。
- **§1 は「要点の表（正本の列つき）」と「まだ決めていない点の表」だけ。** 決めたことを表と箇条書きの両方に書かない。原文がドラフトで決定が無いなら「決めたこと」の行に「原文に決定は無い（方針は §2）」と1行で書く。
- **原文に無い穴は報告に書く。** 設計書の「まだ決めていない点」に載せるのは、原文にある未決・原文の矛盾・本人が採った追加だけ。作業中に気づいた穴（担当の無い作業、関係の書かれていない2つの数値など）は報告に挙げて本人に選んでもらう。本人に尋ねられないときは、判断に関わるもの3件までを「（仮）」として載せる。
- **付録は対応表だけ。** 原文の章との対応は「原文 §3 → §4.1」の1行ずつにし、削った理由は書かない（報告に書く）。用語集は意味が2つ以上ある語だけ。原文に要件表が無ければ要件表の付録は作らない。
- **章（`##`）の見出しの直後に図を1つ置く。** 関係は構成図（flowchart）、時間順は工程表（gantt）か処理フロー、差は比較表、抽象的な規則は具体例つきの図。図ごとに範囲を示し、矢印に意味を書く。1枚に全階層を詰めない。
- 原文の業務・要件は保持し、読み順と表現だけを変える。要件の削除・変更と、表現の変更を区別して本人に示す。
- 状態の語を守る: 参考値を実績に、想定を確約に、方針を実施済みに、提案を決定に変えない。未決は `[要確認]` と書き、§1 の「まだ決めていない点」の表に載せる。「別マニュアル参照」で完成扱いにしない。
- **1段落1論点、全角200字以内。** 段落は結論の文から始める。「適切に」「必要に応じて」「〜が重要である」は、誰が・いつ・何を・どの値で、に置き換える。置き換えられなければ削る。条件が3つ以上並ぶなら表にする。
- 検査: `python3 .claude/skills/design-doc/scripts/check_doc.py --render <案件>/design/<文書名>.md`（tool-slides の外なら `python3 ~/.claude/skills/design-doc/scripts/check_doc.py --render ...`）→ `design/_check/<文書名>-fig-NN.png` を Read で全枚目視（文字の重なり・はみ出し・矢印の向き・色の意味）。VSCode の Markdown プレビューで見るには拡張機能「Markdown Preview Mermaid Support」が要る。Notion に貼る場合も Mermaid のコードブロックはそのまま図になる。

## フェーズ3: 確認型スライド（`index.qmd`。slides の4フェーズに従う）

型の規約・マークアップ・見本は `references/confirm_deck.md`。要点:

- 意思決定者には「決めてもらう」のではなく「決めたことを伝えて齟齬を確かめる」。**1枚＝決めたこと1つ＋確認点1つ。**
- YAML の直後の記録に `<!-- kind: confirm -->` を足す。各枚に `<!-- claims: C1,C2 -->`（主張の表の id）。
- 1枚目: 「〜について決めたN点をお伝えします。認識と違う点があれば指摘してください」。左に決めたN点（2枚目以降の見出し）、右に `::: {.undecided}` の「まだ決めていない点」。
- 2〜N枚目: 決めたこと1つを「〜します」で言い切るタイトル、その対照表・条件・図、下端に `::: {.check}` の確認点（「〜に違いがないか」「〜とずれていないか」「〜と、満たさない場合の扱い」）。
- 最後の枚: 体制と進め方（担当・工数・時期）で終える。取れていない数字は `[要確認]{.tbd}`（灰の点線の枠）で残す。
- 付録: 設計書で片付ける整理（規則の統一、本番構成の番号）と主張の表の一覧。本編の話題にしない。
- ゴースト段階は `<!-- check: 確認点 -->` のコメントで骨子（タイトル＋確認点）を見せ、承認後に `::: {.check}` にする。雛形は `decks/_template_confirm/index.qmd`。
- 検証は slides のフェーズ4（lint → `render_check.sh` → 全枚 Read）。見本と見比べる点: タイトルが2行以内、確認点の帯が下端に1本、点線の枠が未決の値だけ、付録に「付録」の印。

## フェーズ4: 原文との照合（両方の成果物）

成果物ごとに次を確かめ、結果を本人への報告に書く。lint 合格だけで「分かりやすくなった」とは言わない。

1. **状態の保持**: 参考値→実績、想定→確約、方針→実施済み、提案→決定 への格上げが無い（`claims.csv` の status と本文の語を突き合わせる）。
2. **落としていないもの**: 人の定期作業と承認、費用の未確定、失敗時の回復。削った段落の一覧を読み直し、決定・条件・担当・数値が混じっていないかを確かめる（`claims-unused` の warning も見る）。
3. **矛盾の扱い**: 現行と変更後、判定規則、組織名を想像で統一していない（統一したなら 提案 として本人が採った記録がある）。
4. **参照**: 要件表・章参照のずれを検出し、無い内容を生成していない。
5. **読者テスト**: 成果物だけを読んで「今回は何を決めた（決める）か」「正常時と失敗時に誰が動くか」「どの根拠がまだ無いか」「次の段階へ進めるのはいつか」に答えられる。原文で未決なら、答えを創作せず未決の箇所を示せる。

AI による読者役の点検と、実際の意思決定者の理解の確認は区別して報告する。効果（所要時間・答えられなかった問い・修正回数）は、同じ題材の改善前後と、別分野の設計書で比べてから一般化する。

## やらないこと（理由）

- 要約で縮めない: 条件・例外・担当を言い換えて短くすると、そこが落ちる。段落を丸ごと削るか、繰り返しを1か所にまとめる。残す段落は主張の表に戻して組み替える。
- 構造を足して長くしない: 状態の列・主張ID・対照表・付録は読み手の道具だが、同じ事実を表ごとに書き直すと、一般論を消しても読む量が原文の2倍以上になる（2026-10-02 の試験で、Opus・Sonnet とも原文の約2.6倍になった）。
- 一般論を残して「丁寧な設計書」に見せない: 中身の無い段落は、読み手が中身のある段落を探す手間を増やすだけで、何も決めていない（coherence 効果）。
- 原文に無い費用・日程・性能を補わない: 不確実な箇所ほど LLM は水増しする（verbosity compensation）。未決と書けば本人が埋める。
- 「決めてもらう」構成にしない: 本人の決定（2026-10-01）。どうするかはこちらで決め、意思決定者の時間は齟齬の確認に使う。
- 未決の印 `[要確認]{.tbd}` で placeholder の検査をすり抜けない: 一覧（`.undecided`）に載せて初めて許される。
- 複数の文書に同じ共通事項の全文を複製しない: 短い要点と、定義の正本・版への参照にする。
