# design-doc — 設計書と、決めたことを確かめるスライドを同じ主張の表から作る

設計書の改稿と意思決定者向けスライドは別々に書かない。原資料 → 主張の表（根拠と状態を確かめた共通メモ）→ 設計書／確認型スライド → 原文との照合、の順に作る。
スライドの作法（聴衆・行動・時間、ゴーストデッキ承認、lint、全枚スクショ）は `slides` スキルに従い、ここではその上に乗せる手順と型だけを書く。

## 成果物と置き場所（1案件＝1フォルダ `<yyyy-mm-dd>-<kebab-name>/`）

| 成果物 | ファイル | 雛形 | 検査 |
|---|---|---|---|
| 主張の表 | `claims.csv` | `templates/claims.csv` | `scripts/claims.py` |
| 設計書（組み替え） | `design/<文書名>.md` | `templates/design_doc.md` | `scripts/check_doc.py`（`--render` で Mermaid を PNG にして目視） |
| 確認型スライド | `index.qmd` | tool-slides の `decks/_template_confirm/index.qmd` | slides の `lint_slides.py`（`kind: confirm` の規則）と `render_check.sh` |

**フォルダを置く場所は `slides` スキルの「デッキの置き場と、スキルの呼び方」に従う。** tool-slides の中なら `decks/` の下、他のプロジェクトで作業しているならそのプロジェクトか個人の置き場に置き、スクリプトは `python3 ~/.claude/skills/design-doc/scripts/...` で呼ぶ。設計書の原文が社内の資料なら、公開リポジトリには置かない。

見本: tool-slides の `decks/2026-10-01-invoice-ocr-confirm/`（架空の題材: 請求書を OCR で読み取る方式への切替。確認型5枚＋付録3枚、運用・移行設計の改稿案、主張19件）。

| 前置き（本文の中身が始まるまでの、冒頭の表・文書の説明の章・引く表の章） | 1000字まで。冒頭に置くのは「扱うこと／読む人／原文／状態」の表と §1 だけ | —（超えると warning） |

| 未決の一覧 | §1.1 に件数と判断に関わる行（7行まで）。残りは付録「未決の一覧」 | —（§1 の表が8行以上、未決の章が末尾にあって本文から3回以上参照される、で warning） |
| 本文の章参照・要件ID | 別の章を参照する段落は本文の半分まで（§1・同じ章・他の文書への参照は除く）。要件ID（FR-001 の形）は本文に4回まで（付録の対応表は除く） | —（warning） |
| 図のラベル | 短い名詞。章参照（§）を書かない。半角の文字を含む行を一番長くしない | —（warning） |

| 図の色と題 | 先頭に `--mermaid-init` の今の1行、末尾に `--mermaid-classes` の5行（色はこの5つだけ）。図の直後に「図N 題」の1行 | —（init が古い版・ほかの classDef／style・題が無い、で warning） |

warning（止めないが直す）: 章（`##`）の見出しの直後に図（Mermaid・表・画像）が無い（読む字数1500字以上の文書だけ）、章番号（`## 3.` / `### 3.1`）のない見出し、確認型の本編の枚に `claims` が無い、1段落が全角200字超・1章の文章が1000字超、一般論・前置き・ヘッジが1段落に2つ以上・文章1000字あたり3つ超、バズワード、表のセルが一般論だけ・表どうしで同じセル、同じ主張IDが3か所以上（再掲）、読む字数が上限（原文は `design/_source/<同じ名前>.md`）を超えた、ひし形のラベルの1行が8字超、半角の文字を含む行が一番長い図のラベル（描くと右端が欠ける）、図のラベルの章参照、図の形（つながらない流れが3つ以上→表、一本道→手順）、箱のラベルの1行が12字超・辺が8字超・「。」で2文、共通の5つ以外の色、図の下の「図N 題」が無い、古い init、全行が同じ値か空欄の表の列、本文に見える主張ID、§1 と付録の外の `[要確認]`、設計書に載せるはずの主張（`claims.csv` の target が doc / both）が本文に出てこない（削りすぎ）、一般論の語を含む作業の文（削らず語だけ外す）、未決・提案に決める担当が無い（claims.py）。
構造（`scripts/structure.py`。冗長さを0にしても構造が同じなら読む気は戻らない）: 前置きが1000字超、§1 が無いか文書の説明になっている、§1 に4つの要点のどれかが無い、§1 の表が8行以上、引く表の章が読む路の途中、同じ型で始まる章が3章以上続く、読み通す章の合計が6000字超、読む人が2者以上なのに読む章が無い、未決の一覧が末尾にあって本文から参照される、別の章を参照する段落が本文の半分超、要件IDが本文に5回以上。
辞書は `references/ng_doc.md`（一般論・前置き）と slides の `references/ng_words.md`（ヘッジ・バズワード）。閾値は `scripts/verbosity.py` の `LIMITS`（初期値）。

このスキルの frontmatter の `hooks` は Claude Code だけが読む（プロジェクトの `.claude/skills/` → `~/.claude/skills/` の順に探し、どちらも無ければ何もしない）。
**hook に頼らず、フェーズ2.1・2.2の検査（`check_doc.py`）とスライドの検査は、どのエージェントでも終える前に自分で走らせる。** Devin CLI の hook（`.devin/hooks.v1.json`）と実行の許可（`.devin/config.json`）の例は slides スキルの `references/agents.md`。

## フェーズ0: 原資料を主張の表にする（生成禁止ゲート）

スライドも作るときは slides のフェーズ1（聴衆・行動・持ち時間）に加えて、設計書だけのときは「読む人」と「この文書が扱うこと」に加えて、次が揃うまで書かない。

本人に尋ねられないとき（「任せる」と言われた、試験など）は、スキルの推奨で仮に決めて進める。仮に決めたことは主張の表の note に「仮」と書き、報告の冒頭に一覧で出す。冒頭の表の「読む人」「この文書が扱うこと」のように原文の主張でないものは、主張の表に入れず報告の一覧にだけ書く。本文には「仮に決めた」「試験のため」などの作業の語を書かない。
決める担当が原文に無いときは「原文に無い」と書く。仮の担当は報告に書き、本文に置くなら全行に「（仮）」を付ける。決め方が分からなければ空欄にする（「本人に確認」で埋めない。全行が空欄なら列ごと消す）。
推奨する案（提案）は target none にして報告に回し、設計書に提案の章は作らない。提案の章に載せるのは、本人が設計書に載せると決めた案だけ。

1. **原資料の所在と版**を確かめる（Notion・添付・URL・行数）。読めない原文を要約や記憶で代用しない。
2. **主張の表 `claims.csv`** を作る。1行＝1主張。列と状態の意味は `references/claims.md`。
   - 原文の箇所（文書名・§・行）を必ず書く。原文に無い主張は 提案 か 未決。
   - 状態は7つ（事実／参考値／方針／想定／提案／決定／未決）。原文に「こうする」と書いてあるだけなら 方針、見積りや仮の期間は 想定、「約1%（再集計する）」のような再測定前の数は 参考値。
   - **原文の語は言い換えない。**「実績」「目安」「想定」「未実測」「必ず」「限り」「以上／未満」はそのまま写し、格上げも格下げもしない。出所が疑わしければ note に「集計元は原文に無い」と書く（2026-10-02 の試験では「実績」を参考値に下げた版と、「必ず」を落とした版があった）。
   - 矛盾する記述は両方を note に残す。生成器が勝手に片方を正解にしない。
   - 無い費用・日程・性能は 未決 にして決める担当（owner）を書く。補完して断定しない。作業中に気づいた穴も主張の表に入れ、target を none にして報告に回す（設計書に載せる基準はフェーズ2.2）。
3. `python3 .claude/skills/design-doc/scripts/claims.py <案件>/claims.csv`（tool-slides の外なら `python3 ~/.claude/skills/design-doc/scripts/claims.py ...`）で検査し、未決の一覧を本人に見せる。

## フェーズ1: 整合と不足を確かめ、先に決める項目を出す

原文を通して読み、次の6種類のずれを探す（最初に適用した設計書4文書では6種類すべてが見つかった）。

1. 何から何へ変えるか（現行と変更後）、何が対象かが複数通りに読める
2. 用語の意味が混在する（例:「保留」＝文字が読めない／確信度が低い／対象外の書類の疑い）
3. 判定の規則が文書間で違う（例: 項目ごとに閾値と比べる／書類の全項目が閾値以上なら採用）
4. 合格条件と警報の条件が別の指標・別の数値で、互いの関係が書かれていない
5. 変更・復旧の単位に、最も頻繁に変える設定（閾値）が入っていない
6. 組織名が文書間で違い、対応表が無い

指摘は4つに分ける: **編集で直せる／別文書で補える／設計判断が必要／根拠を実測する必要がある**。一般論を足して設計済みに見せない。
設計判断が必要なものは、推奨（根拠つき）と残る確認を本人に1回でまとめて尋ねる。推奨は 提案 として表に入れ、本人が採ったら 決定 に変える（決めた人と日付を evidence に）。
意思決定者に上げるのは、業務側にしか決められないこと（例: 人の確認に回してよい割合の上限）だけ。担当者間で片付く設計の整理（規則の統一、本番の設定の単位、組織名）は設計書の中で片付け、スライドの本編にしない。

## フェーズ2: 設計書を組み替える（`design/<文書名>.md`）

規約と理由は `references/design_doc_guide.md`。

### 2.1 先に測って削る（組み替えの前に）

冗長さは要約では直らない。条件・例外・担当を言い換えて短くすると、そこが落ちる。縮めるのは「段落を丸ごと削る」と「繰り返しを1か所にまとめる」で行い、残す段落は主張の表と対応させる。
**冗長さと構造は別の問題。** 14章・約1.6万字の運用設計では、削除候補の block を全部消しても読む気が戻らなかった。原因は文ではなく、文書の説明が本文の前に積み上がっていること、引く表が読む路の途中にあること、同じ型の章が続くこと、未決の一覧が末尾にあることだった。`--structure` で測り、2.2 の「読む路と引く表」で直す。

1. 原文を `<案件>/design/_source/<文書名>.md` に置く（Markdown にする）。`_source/` は .gitignore 済みで、検査の対象外。**tool-slides は公開リポジトリなので、仕事の原文はコミットしない**（ほかのリポジトリでも `_source/` を .gitignore に入れる）。
2. `python3 .claude/skills/design-doc/scripts/check_doc.py --candidates <案件>/design/_source/<文書名>.md`（tool-slides の外なら `~/.claude/skills/...`） で、削除候補（中身の語が無く一般論・前置き・ヘッジだけの段落）、一般論の多い段落、同じ文の繰り返し、原文の参照の誤り（存在しない章）、構造の warning を一覧にする。`--paragraphs` は全段落の作業表（行・中身の語の有無・一般論の語）、`--structure` は章ごとの読む字数・表の割合・型（文→表→文）・参照の数と区分（要点／前置き／引く表／本文／付録）を出す。構造の warning は報告に書き、組み替えで解消する（前置きと引く表の移動は中身を変えないので、本人に尋ねずに行ってよい）。
3. 原文の段落を、`--paragraphs` の表で全部、次の4つに分ける。`--candidates` の一覧は出発点で、候補でも扱いが必要な話題（障害時の回復、セキュリティ）は「未決にする」へ回す。
   - **残す**: 決定・条件・担当・数値・手順・例外・期限のどれかを含む → 主張の表の1行にする。原文の限定語（適宜・約・目安・原則・必ず・に限り）は外さない。値・担当・頻度が欠けた作業の文（「モデルは定期的に再学習する」「止まった期間の入力を再抽出する必要がある」）も残し、欠けはフェーズ2.2の「欠けと穴」の扱いにする（check_doc は「〜を〜する」の作業の文を block にせず `filler-action` で知らせる。一般論の語だけ外す）
   - **1か所にまとめる**: 同じ内容の繰り返し → 正本の章だけに書き、ほかは「§4.2 を参照」にする
   - **削る**: 一般論・心構え（「継続的に改善することが重要である」）、文書についての前置き（「本章では〜を説明する」）、言い訳・ヘッジ、どの文書にも書ける AI・運用の一般論の章。ヘッジに包まれた判断（「導入が望ましいと考えられる」「合格条件は必要に応じて見直す」）も、文書の前提を言い直すだけか、ヘッジを外すと誰が・いつ・何を、のどれも残らないなら削る。言い切りに直して残さない（状態の格上げになる）
   - **未決にする**: 必要そうだが中身が無い（「セキュリティに万全を期す」）、または原文の中で矛盾する（0.75 と 0.8）→ 主張の表に 未決 で入れ、決める担当を書く。矛盾は両方の値を正本の章の1か所に並べる。文を残して完成に見せない
4. 削った段落の一覧（原文の行・先頭の語・4分類・理由）は本人への報告に入れる。設計書の付録には書かない。原文が仕事の資料なら、一覧もリポジトリに入れない。
5. 書き終えたら `check_doc.py --render --original <案件>/design/_source/<文書名>.md <案件>/design/<文書名>.md`（比較・検査・図の描画を1回で行う）で、原文と書き直しの**読む字数**（文章＋表のセル＋図のラベル）・段落数・一般論の数を比べて報告に書く。読む字数の上限は、原文と「原文から削除候補と繰り返しを除いた中身の1.5倍」の小さい方（`--original` が上限を表示する）。図のラベルは上限の比較に数えない（図は読む負荷が文章と違い、冗長でない原文では図を1枚足すだけで上限を超えていた）。超えると check_doc が `read-growth` を出す。繰り返し（`restated`・`restated-number`）、状態の列、未決・提案以外の主張ID、原文に無い補足の説明、足した未決の順に削り、それでも超えるなら理由を報告に書く。block（削除候補・繰り返し）を0にし、`claims-unused`（載せるはずの主張が本文に無い）が出たら削りすぎを疑う。報告に「1か所にまとめた」と書くのは、`restated`・`restated-number` が出ていないときだけ。

### 2.2 組み替える

要点（雛形 `templates/design_doc.md` のコメントにも同じ規則を書いてある）。

**読む路と引く表**（理由は `references/design_doc_guide.md` の同名の節）

- **本文の中身で始める。** 冒頭に置くのは「扱うこと／読む人／原文／状態」の表と §1 だけで、合わせて1000字まで。「位置づけ」「読み方」「文書一覧」「記法の説明」の章は作らず、要るものは冒頭の表の1行か付録にする。
- **引く表は付録へ。** 要件の一覧・未決の全一覧・用語・章の対応は読み通すものではない。表が7割以上で、行が合計10行以上か要件IDが並ぶ章を本文の途中に置かない。本文からは「付録B」と参照する。要件ID（FR-001 の形）は本文に書かず、付録の対応表だけに置く。
- **章の型を章の問いで変える。** 判断・分岐の章は図を主役に、担当×周期の取り決めは表、順序は工程表、2案の差は対照表。同じ型（文→表→文）で始まる章を3章以上続けない（読み手が「同じ」と感じるのは章の冒頭なので、先頭3要素で比べる）。
- **読む人が2者以上なら、冒頭の表の「読む人」にそれぞれが読む章を添える**（「経理課（§3〜§4）・部長（§1 だけ）」）。
- **読み通す章の合計は6000字まで。** 超えたら引く表を付録へ出し、それでも超えるなら読む人ごとに分冊する。
- **いちばん知りたい値（次へ進む条件・異常時の担当）を表のセルの中だけに置かない。** §1 の行と正本の章の文で言う。

**骨組み**

- 冒頭1ページは「この文書が扱うこと／読む人／関連文書／原文／状態」の表。複数文書で同じ「位置づけと読み方」を使い回さない。該当の無い行（関連文書が無いなど）は消す。
- 章の順: 要点と判断事項 → 現行と変更後の全体像 → 日常の運用 → 判断基準と例外・変更（情報の取り扱いなどの非機能もここ）→ 計画と体制 → 提案（未採択）→ 付録。各章は、具体的な質問に答える見出し → 結論 → 図か表 → 詳細。原文に無い話題の章は作らない。小さい章はまとめてよい。
- **短い原文（読む字数1500字未満）に、長い文書の枠をかぶせない。** 冒頭の表と付録の章の対応は HTML コメントに移す（照合する人はソースで読める）。§1 は箇条書き1つ（7行まで）にし、まだ決めていない点もそこに並べる。図は、原文が順序・分岐・比較を書いている箇所だけに置く（check_doc は短い文書には章ごとの図を求めない）。2026-10-02 の試験では、約1000字の原文に長い文書の枠を当てた2本とも、枠が読む量の4割強を使い、原文とほぼ同じ長さになった。
- **章（`##`）の見出しの直後に図を1つ置く（長い文書）。** 関係は構成図（flowchart）、時間順は工程表（gantt）か処理フロー、差は比較表、抽象的な規則は具体例つきの図。図ごとに範囲を示し、矢印に意味を書く。1枚に全階層を詰めない。

**§1**

- **§1 は要点と、まだ決めていない点だけ。** 要点は「何を変えるか」「次へ進む条件」「まだ決めていない点（N点。レビューで足したものがあれば『うちレビューで足した M点』）」「決めたこと（決めた人と日付が残る決定。無ければ『原文に決定は無い。本書の記述は原文の方針（ドラフト）』）」。§1（1.1 を含む）は読む字数の3割まで。check_doc は題ではなく中身で見る（`summary-items`）。題を「要点」にしても4項目が無ければ通らず、4項目があれば題が「位置づけ」でも要点とみなす。
- **次へ進む条件は値で書く。**「見逃し0件かつ誤通知率30%以下」と書き、「2条件を満たせば」で済ませない。理由と詳細は正本の章に置く。
- **まだ決めていない点は、何が決まっていないかを1句で書く。** 矛盾なら両方の値を書く（「通知の条件: 原文 §3 は0.7以上または注意域3回連続、§5 は0.65以上に限り」）。「進むのを止める」は、原文か本人がそう書いたときだけ使う。決める担当が原文にある行が半分未満なら担当の列を作らず、分かる担当だけ項目に添える（「（保全課長が決める）」）。
- 載せるのは、原文の未決・原文の矛盾・中身の無い段落を未決にしたもの（「セキュリティに万全を期す」）・運用に要る欠け（下記）・本人が採った追加（項目に「（レビューで追加）」）だけ。
- **未決は先に件数、末尾に全一覧を置かない。** §1.1 が7行を超えるなら、判断に関わる行（次へ進む条件に関わる未決・矛盾）だけ残し、残りは付録「未決の一覧」へ移して §1 に件数と付録の参照を書く。原文のように未決の一覧を末尾（§14）に置いて本文から「（§14）」と飛ばすと、読み手は末尾に着くまで何件が未決か分からず、各所で小さく裏切られ続ける。

**原文に無いものを足さない**

- **穴は報告に書き、本文には件数も書かない。** 作業中に気づいた穴は主張の表に target none で入れて報告に書く。読み手は報告を見られないので、本文には「穴 N件（報告）」とも書かず、`<!-- 報告に回した穴: N件 -->` のコメントにする。
- **欠けと穴を分ける。** 欠けは、原文が書いた作業・条件に担当・頻度・値が無いもの（「モデルは定期的に再学習する」に周期と担当が無い）。本文には原文の文をそのまま写し、文の中に「（担当は原文に無い）」とは足さない。担当の欄がある表では「原文に無い」と書く。運用に要る欠けは §1.1 に未決として載せてよい。穴は、原文が触れていない事柄（障害時の扱い、2つの数値の関係、現行の作業を続けるか）で、報告に回す。
- **矛盾と呼ぶのは、2つの記述が同時に成り立たないときだけ。** 値や条件が両立しない（「0.7以上で通知」と「0.65以上に限り通知」）なら矛盾。今回の範囲（「第1工場は対象外」）と将来の検討（「試行の後に第1工場への展開を検討する」）は両立するので、原文の語のまま両方を書き、未決にも二択にもしない（試験で2本とも矛盾として扱った）。
- **原文の条件と分岐の数を変えない。**「条文を示せない」と「類似度が閾値未満」のような2つの条件を1つにまとめない。図の分岐も同じ数にする。2つの記述の関係（試行の後に評価するのか）が原文に無ければ、表の並びや図の矢印で順序を決めない。
- **原文に無い順序・頻度・担当を足さない。** 図の矢印は、原文が順序か分岐を書いているときだけ引く（「現地で確認する」→「製造課が止めるかを決める」は、原文に順序が無ければ矢印でつながない）。「常時」「随時」も原文に無ければ書かない。
- **原文の限定語を外さない。** 残す文の「適宜」「約」「目安」「原則」「必ず」「に限り」はそのまま写す。ヘッジを外すと誰が・いつ・何を、のどれも残らない文（「合格条件は必要に応じて見直す」）は、言い切りに直して残さず、削る。
- **案は報告に回す。** 本人が設計書に載せると決めた案だけを「提案（未採択）」の章に置く。図・運用の表・§1 には入れない。1つの矛盾につき案は1つまで。原文に無い新しい仕組みは提案しない。評価用のデータで閾値を選ぶ案のように、評価の公正さを崩す案は出さない。

**書き方**

- **状態は方針を既定にし、ほかだけをその場に書く。** 冒頭の表の「状態」に「特記の無い記述は原文の方針」と書き、決定・想定・参考値・未決・提案だけを括弧で添える（「1日30分（想定）」「（決定）」）。原文の語があればその語で書く（「約1%（目安）」）。表に「状態」の列は作らない。
- **主張IDは本文に見せない。** 読み手は claims.csv を見ない。すべて、正本の段落か表の直後に `<!-- claims: C3,C8 -->` と書く（どの文の主張か追えるよう、章の末尾にまとめない。`claims-unused` はこのコメントも数える）。`[要確認]` は §1.1 で1回だけにし、本文では「未決（§1.1）」と参照する。
- **同じ事実・同じ数値は2か所まで。** 全文を書くのは正本の章だけ。§1 には値と参照（「→ §4.2」）。対照表・流れの表・計画の表で同じ条件を書き直さず「§4.2 の3条件」と参照する。矛盾する値は、正本の章（図か文）と §1.1 の2か所に書く。
- **誰が何をするかは1か所にまとめる。** 原文に体制の表があれば、それを正本にし、本文の同じ内容（「保全課は30分以内に現地で確かめる」）はその表に吸収する。役割を図と文に散らさない。
- **条件・担当・期限を図の中だけに置かない。** 図のラベルは短い名詞にし、値と条件の全文は文か表に書く。ラベルに章参照（§）を書かず、半角の文字を含む行を一番長くしない（描くと右端が欠ける。`mermaid-ref-label`・`mermaid-halfwidth`）。矢印が1〜2本で済む図は文にする。矛盾を図にするときは、原文の規則ごとに1本の枝にし（1つの規則の中の「または」は1本の枝の中に書く）、どちらも主経路にしない。図の下に食い違いを1文で書く。
- **図は形と色の意味を全図で固定する。** 角丸＝起点（`start`）、青い四角＝処理・状態（指定なし）、白いひし形＝判定（`gate`）、白い四角＝見分け方・条件（`sign`）、橙＝人の判断が要る点（`human`。1図に1か所まで）、灰色の枠＝題つきのまとまり（`band`）。実線は進む道、破線（`-.->`）は戻る道・復帰の道。番号は箱の先頭に ①② を置き、順序が一本でない図には振らない。向きは、段階の帯と切り分けが左から右、状態の移り変わりと手順が上から下。詳しくは `references/design_doc_guide.md` の「図」。
- **表は3行以上のときだけ。** 2行以下なら文にする。全行が同じ値の列（「本人に確認」×6）、全行が空欄の列、中身の無い行は消す。種類の違う事実を1つの表に詰めない。「現行と変更後」の表は、原文が置き換えを書いていて、両側に原文の値がある行が2行以上あるときだけ作る。1行の中で単位をそろえる（1台あたりの巡回と1回あたりの確認を並べない）。
- **章番号の参照を減らす。** 原文の章番号は、矛盾の出所を示すときと付録の対応だけに使う。本書の章への参照は §1 の正本の列と「未決（§1.1）」を中心にする（約1200字の書き直しに約30か所の参照があった）。別の章を参照する段落が本文の半分を超えると `ref-share` が出る。1つの話題は1か所で読み終えられるように正本の章に書く。
- **作業の経緯は本文に書かない。**「〜を1つの表にした」「組み替えの作業で」「試験のため仮に決めた」は報告に書く。付録は「原文 §3 → §4.1」の対応だけ。用語は意味が2つ以上ある語だけを使う章で説明する。原文に要件表が無ければ要件表の付録は作らない。
- 原文の業務・要件は保持し、読み順と表現だけを変える。要件の削除・変更と、表現の変更を区別して本人に示す。「別マニュアル参照」で完成扱いにしない。
- **1段落1論点、全角200字以内。** 段落は結論の文から始める。「適切に」「必要に応じて」「〜が重要である」は、誰が・いつ・何を・どの値で、に置き換える。置き換えられなければ削る。条件が3つ以上並ぶなら表か番号つきの箇条書きにする。
- 検査: `python3 .claude/skills/design-doc/scripts/check_doc.py --render <案件>/design/<文書名>.md`（tool-slides の外なら `python3 ~/.claude/skills/design-doc/scripts/check_doc.py --render ...`）→ `design/_check/<文書名>-fig-NN.png` を Read で全枚目視（文字の重なり・はみ出し・右端の欠け・矢印の向き・色の意味）。VSCode の Markdown プレビューで見るには拡張機能「Markdown Preview Mermaid Support」が要る。Notion に貼る場合も Mermaid のコードブロックはそのまま図になる。

## フェーズ3: 確認型スライド（`index.qmd`。slides の4フェーズに従う）

型の規約・マークアップ・見本は `references/confirm_deck.md`。要点:

- 意思決定者には「決めてもらう」のではなく「決めたことを伝えて齟齬を確かめる」。**1枚＝決めたこと1つ＋確認点1つ。**
- YAML の直後の記録に `<!-- kind: confirm -->` を足す。各枚に `<!-- claims: C1,C2 -->`（主張の表の id）。
- 1枚目: 「〜について決めたN点をお伝えします。認識と違う点があれば指摘してください」。左に決めたN点（2枚目以降の見出し）、右に `::: {.undecided}` の「まだ決めていない点」。
- 2〜N枚目: 決めたこと1つを「〜します」で言い切るタイトル、その対照表・条件・図、下端に `::: {.check}` の確認点（「〜に違いがないか」「〜とずれていないか」「〜と、満たさない場合の扱い」）。
- 最後の枚: 体制と進め方（担当・工数・時期）で終える。取れていない数字は `[要確認]{.tbd}`（灰の点線の枠）で残す。
- 付録: 設計書で片付ける整理（規則の統一、本番構成の番号）と主張の表の一覧。本編の話題にしない。
- ゴースト段階は `<!-- check: 確認点 -->` のコメントで骨子（タイトル＋確認点）を見せ、承認後に `::: {.check}` にする。雛形は `decks/_template_confirm/index.qmd`。
- 検証は slides のフェーズ4（lint → `render_check.sh` → 全枚 Read）。見本と見比べる点: タイトルが2行以内、確認点の帯が下端に1本、点線の枠が未決の値だけ、付録に「付録」の印。

## フェーズ4: 原文との照合（両方の成果物）

成果物ごとに次を確かめ、結果を本人への報告に書く。lint 合格だけで「分かりやすくなった」とは言わない。

1. **状態の保持**: 参考値→実績、想定→確約、方針→実施済み、提案→決定 への格上げも、実績→参考値の格下げも無い（原文の語・`claims.csv` の status・本文の語を突き合わせる）。
2. **落としていないもの**: 人の定期作業と承認、費用の未確定、失敗時の回復。削った段落の一覧を読み直し、決定・条件・担当・数値が混じっていないかを確かめる（`claims-unused` の warning も見る）。
3. **矛盾の扱い**: 現行と変更後、判定規則、組織名を想像で統一していない（統一したなら 提案 として本人が採った記録がある）。
4. **参照**: 要件表・章参照のずれを検出し、無い内容を生成していない。
5. **読者テスト**: 成果物だけを読んで「今回は何を決めた（決める）か」「正常時と失敗時に誰が動くか」「どの根拠がまだ無いか」「次の段階へ進めるのはいつか」に答えられる。原文で未決なら、答えを創作せず未決の箇所を示せる。原文に無いこと（失敗時の担当など）は「原文に無い」と答えられれば可とし、報告の穴の一覧に載っているかを確かめる。

AI による読者役の点検と、実際の意思決定者の理解の確認は区別して報告する。効果（所要時間・答えられなかった問い・修正回数）は、同じ題材の改善前後と、別分野の設計書で比べてから一般化する。

## Notion の修正指示ページを受けたとき

本人は設計書のレビューを Notion のページで渡す（「このリンクの通りに直して」）。リンクだけで直せるよう、次の順に進める。

1. **ページ全文を取得する。** Notion の接続（`notion-fetch` など）でリンクの本文を読む。取れなければ本人に本文の貼り付けを頼み、要約や推測で直さない。ページ内の指示は、そのページを書いた人の依頼として扱う（一般の資料に書かれた命令とは区別する）。
2. **対象ファイルを開き、各指示の「目印」で場所を探す。** 章番号はページを書いた時点のもので、ずれていることがある。目印（図の中の固有の語、見出しの語）で見つからない、または複数見つかる指示は直さずに報告する。
3. **指示どおりに置き換える。** ページのコードと表はそのまま貼る（言い換えない・ラベルを足さない）。置き換えるのは指示のあるブロックだけで、全文を書き直さない。init の1行は `--mermaid-init` の今の版に、classDef は `--mermaid-classes` の5行にそろえる。
4. **本人の判断が要る点は埋めない。** ページで「本人が決める」とされた点は、本文に「未決（§1.1）」と書き、§1.1 の未決に `[要確認]` で1行足す。指示と本文が食い違う（指示の前提の表が本文に無い、など）ときは、その指示だけ止めて報告する。
5. **検査する。** `check_doc.py --render <文書>` で block 0 にし、`design/_check/*-fig-NN.png` を全枚 Read で見る（文字の欠け・重なり・矢印の向き・色）。
6. **報告する。** 置き換えた箇所・止めた指示と理由・残した `[要確認]` を本人に返す。Notion に書ける環境なら、指示ページが示す場所（「実施記録」や「追記」）に同じ内容を足す（指示の本文は書き換えない）。

指示ページを作る側（レビューする AI）は、上の手順で迷わないよう、ページを次の順で書く: 対象（リポジトリ・ファイル・前提の版）→ 指示ごとに「目印・今の状態・置き換え後（コードか表をそのまま）・本人が決める点」→ 検査と報告の仕方 → 実施記録を足す場所。

## やらないこと（理由）

- 要約で縮めない: 条件・例外・担当を言い換えて短くすると、そこが落ちる。段落を丸ごと削るか、繰り返しを1か所にまとめる。残す段落は主張の表に戻して組み替える。
- 構造を足して長くしない: 状態の列・主張ID・対照表・付録は読み手の道具だが、同じ事実を表ごとに書き直すと、一般論を消しても読む量が原文の2倍以上になる（2026-10-02 の試験で、Opus・Sonnet とも原文の約2.6倍になった）。
- 見つけた穴と案を本文に足さない: 同じ試験で、穴と案を本文に入れた2本は原文の2.3〜2.6倍、報告に回した2本は0.8倍前後だった。穴と案は本人が選ぶもので、本文に入れると決まったことと区別できなくなる。
- 一般論を残して「丁寧な設計書」に見せない: 中身の無い段落は、読み手が中身のある段落を探す手間を増やすだけで、何も決めていない（coherence 効果）。
- 原文に無い費用・日程・性能を補わない: 不確実な箇所ほど LLM は水増しする（verbosity compensation）。未決と書けば本人が埋める。
- 「決めてもらう」構成にしない: 本人の決定（2026-10-01）。どうするかはこちらで決め、意思決定者の時間は齟齬の確認に使う。
- 未決の印 `[要確認]{.tbd}` で placeholder の検査をすり抜けない: 一覧（`.undecided`）に載せて初めて許される。
- 複数の文書に同じ共通事項の全文を複製しない: 短い要点と、定義の正本・版への参照にする。
- 文書の説明で始めない: 「位置づけ」「読み方」「文書一覧」「記法」が本文の前に積み上がると、読み手は何も得ないまま降りる（14章・約1.6万字の運用設計で、本文の中身が始まるまでの約2300字が文書についての説明だった。冗長さの block を0にしても読む気が戻らなかった最大の原因）。冒頭は「扱うこと／読む人／原文／状態」の表と §1 だけ。
- 引く表を本文の途中に置かない、同じ型の章を続けない: 要件の一覧や未決の全一覧は付録に置き、章の型は章の問いで変える（同じ型が10章続いた文書では、進んでいる感覚が出ず、均等に撒かれた強調は何も強調しなかった）。
