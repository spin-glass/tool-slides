## 文書の役割分担（4文書の例）

- **基本設計**: 何を変えるか、誰から何を受け取り、どの結果を返すか。判定規則・データ契約の正本。
- **処理設計（ML設計など）**: どの処理・版・承認済みの設定で結果を作り、更新・復旧するか。
- **精度検証**: 何を正解とし、どのデータで測り、どう合否を決めるか。指標・合格基準の正本。
- **運用・移行**: 誰がいつ確認・対応し、どの条件で次へ進むか。定常作業・異常対応・移行判断。

共通事項の全文を4か所に複製しない。短い要点と、定義の正本・版への参照にする。文書の担当範囲が重なると、同じ用語・数値・判定条件の意味がずれる（最初に適用した4文書では判定規則が2通り、組織名が3通りあった）。

## 構成

- **冒頭1ページは「この文書が扱うこと／読む人／関連文書／原文／状態」の表。** 読者は自分が読むべき文書と節を最初の画面で知りたい。複数の文書で同じ「位置づけと読み方」を使い回すと、本文に無い章を指したままになる。短い原文（読む字数1500字未満）では、この表と付録の章の対応を HTML コメントに移す（試験では、約1000字の原文の書き直しで、冒頭の表・§1・付録の枠が読む量の4割強を使った）。
- **§1 は4つの要点（何を変えるか・次へ進む条件・まだ決めていない点・決めたこと）と、まだ決めていない点の一覧。** 意思決定者は §1 だけ読む。次へ進む条件は値で書く（「2条件を満たせば」では、冒頭だけ読む人が判断できない）。まだ決めていない点は、何と何が食い違うかを1句で書く。「進むのを止める」は原文か本人がそう書いたときだけ使う（原文に無い重みを足す）。未決を冒頭に出すと、確定した仕様として読まれない。
- **章の順は、要点 → 全体像（現行と変更後の対照）→ 日常の運用 → 判断基準と例外・変更 → 計画と体制 → 提案（未採択）→ 付録。** 具体的な利用場面 → 入力と出力 → 通常時と例外時の流れ → 重要な設計判断と理由、の順が読みやすい。14章に一般論が分散すると、現状・担当・判断条件がつながらない。
- **各章は、具体的な質問に答える見出し → 結論 → 図か表 → 詳細。**「明日アラートが出たら誰が何を判断するか」「次の段階へ進めるのはいつか」に答えられる単位で章を切る。
- **付録には原文の章との対応と、要件表のずれだけを置く。** 本文は読み順、付録は参照用。原文の内容を落とさないために対応表を付ける。用語は意味が2つ以上ある語だけを、使う章で説明する。

## 読む路と引く表

冗長さ（一般論・繰り返し）と構造は別の問題。14章・約1.6万字の運用設計（2026-10-05）では、削除候補の block を全部消しても読む気が戻らなかった。文の単位ではよく書けていた（各節が結論から始まり、理由も書いてある）。直すべきは文ではなく、置く場所と順序だった。`check_doc.py --structure` が章ごとに測る。

- **本文の中身で始める。** 冒頭に置くのは「扱うこと／読む人／原文／状態」の表と §1 だけ（合わせて1000字まで）。「位置づけ」「読み方」「文書一覧」「記法の説明」は、要るものを冒頭の表の1行か付録にする。この運用設計では、本文の中身が始まるまでの約90行・約2300字が文書についての説明で、読み手は何も得ないまま記法の説明を3つ覚えさせられてから本題に着いた。ここで多くの人が降りる。読む気への効き方は、6つの原因のうちこれが最も大きかった。
- **引く表は付録へ。** 要件の一覧・未決の全一覧・用語・章の対応は読み通すものではなく、必要なときに引く。表が7割以上で、行が合計10行以上か要件IDが並ぶ章を本文の途中に置くと、読み手はそこで止まる（要件IDが14回並ぶ表の章が3番目にあり、本題に入る前に越えなければならなかった。1つの表は8行だったので「1つの表が10行以上」では拾えず、行の合計と要件IDの数で拾うようにした）。本文からは「付録B」と参照する。
- **章の型を章の問いで変える。** 判断・分岐の章は図を主役に、担当×周期の取り決めは表、順序は工程表、2案の差は対照表。同じ型（太字の結論→表→補足の文）で始まる章が14章中10章あると、どの章も同じ手触りで進んでいる感覚が出ない。強調が均等に撒かれると何も強調されない。検査は章の先頭3要素で比べる（全長で比べると末尾の違いで一致せず、この文書でも2章しか続かなかった）。
- **§1 は題ではなく中身。** 「要点」と題を変えるだけで通る検査は、中身を揃える動機にならない。4つの要点（何を変えるか・次へ進む条件の値・まだ決めていない点・決めたこと）が本文にあるかを見る（`summary-items`）。逆に、4項目が揃っていれば題が「位置づけと読み方」のままでも要点の章とみなす。
- **読む人が2者以上なら、それぞれが読む章を添える。** 想定読者を3者と書きながら読む路が1本だと、ある読者が要る2章に着くまでに8章を越える。冒頭の表の「読む人」に「経理課（§3〜§4）・部長（§1 だけ）」と書く。
- **未決は先に件数、末尾に全一覧を置かない。** 未決の一覧が末尾の章にあり、本文の17か所から「（§14）」と飛ばされると、読み手は末尾に着くまで何件が未決か分からず、各所で小さく裏切られ続ける。先に「20件余りが未決で、うち判断に関わるのは2件」と分かっていれば、同じ記述が想定どおりに読める。§1.1 には件数と判断に関わる行（7行まで）、残りは付録「未決の一覧」。
- **いちばん知りたい値を表のセルの中だけに置かない。** 「いつ次へ進めるか」が表の3列目にしか無いと、表を読み、別の章でマージンが未決と知り、末尾で確定条件を見る、の3往復になる。§1 の行と正本の章の文で言う。
- **読み通す章の合計は6000字まで。** 1回で読める量の目安。超えたら引く表を付録へ出し、それでも超えるなら読む人ごとに分冊する。
- **別の章を参照する段落は本文の半分まで。** 6行に1回（約120回）章をまたぐと、1つの話題を読み終えるのに3つの章を往復する。要件ID（FR-001 の形）は読み手に意味を持たない記号なので、本文には要件の内容を書き、ID は付録の対応表だけに置く。

## 図

- **章（`##`）の見出しの直後に図を1つ置き、本文はその説明にする。** 言葉だけより絵を添えた方が理解が上がる（multimedia principle）。注記は図のすぐ下に置く（spatial contiguity）。
- **まず形を選ぶ。** 分岐・合流・戻りがあるときだけ流れ図にする。行と列の対応（いつ・何を・どうする、事象・段・対応）は表、分岐の無い一本道は番号つきの手順にする。2026-10-06 に見た運用設計の図6枚では、互いにつながらない流れの並び（周期ごとの確認、通知の段ごとの対応）と6つの箱の一本道が、図にしたせいで読めなくなっていた（check_doc は `mermaid-shape` で知らせる）。時間順は工程表（gantt）、差は比較表（Markdown の表）、抽象的な規則は具体例つきの図。
- **図形と色の意味を全図で固定する。** 先頭に `check_doc.py --mermaid-init` の1行、末尾に `--mermaid-classes` の5行を貼り、`class` で割り当てる。図ごとに色を決めない（`mermaid-classdef`）。

  | 図形・色 | 意味 | 書き方 |
  |---|---|---|
  | 角丸・灰 | 起点・きっかけ | `A(["取り込みが失敗"])` ＋ `class A start` |
  | 四角・青 | 処理・状態 | `B["手入力へ<br>切り替える"]`（指定なし） |
  | ひし形・白 | 判定 | `G{"条件を<br>満たす？"}` ＋ `class G gate` |
  | 四角・白 | 見分け方・条件 | `C1["画像の形式エラー<br>同じ取引先で繰り返す"]` ＋ `class C1 sign` |
  | 四角・橙 | 人の判断が要る点（1図に1か所まで） | `class T4 human` |
  | 灰色の枠 | 題つきのまとまり | `subgraph ph1["影響を確かめる"]` ＋ `class ph1 band` |

  実線は進む道、破線（`-.->`）は戻る道・復帰の道。破線を使った図は、図の下の題の行に読み方を1文足す。
- **箱には1つのことだけを書く。** 1行は全角12字、辺のラベルは8字まで、2行まで。Mermaid は箱の文字を全角12字ほどで自動的に折り返し、語の途中で切る（「未処／理」「何／件」）ので、意味の切れ目に `<br>` を入れる。「。」で2文を詰めない。辺の長い条件は、辺から出して「見分け方」の箱（`sign`）にする（`mermaid-label`）。
- **番号は箱の先頭に ①② を置く。** 番号だけの行を作らない。悪化の道と復帰の道のように順序が一本でない図には振らない（一本に見えて、4の次に5を読ませてしまう）。
- **向きをそろえる。** 段階の帯と切り分けは左から右（`flowchart LR`）、状態の移り変わりと手順は上から下（`TB`）。描いた幅が本文の幅（900px前後）を超えるなら、向きを変えるか `subgraph` のまとまりで折る（まとまりの中は `direction LR`）。
- **図の直後に「図N 題」の1行を置く。** 「図3 取り込み失敗時の一次切り分け」。読み方の注記は同じ行に1文だけ。「矢印は〜を示す」と書かないと伝わらない図は、矢印の意味が図から読めていない（`mermaid-caption`）。
- **図ごとに範囲を示し、矢印に意味を書く。** `-->|"はい"|` のようにラベルを付ける。何から何へ、どの条件で、が無い矢印は読み手が補うことになる（C4 の点検項目）。図と図の下の文が同じことを言っているか確かめる（矢印は段階1へ戻るのに、文は「段階2に留まる」、の食い違いが実際にあった）。
- **1枚に全階層を詰めない。** 2段まで。3段目が要るなら、その枝だけ別の図にする。
- **ひし形のラベルは1行8字以内。** ひし形は文字が欠けやすい。長い条件は `<br>` で折るか、条件を表に出してひし形には「条件を満たす？」とだけ書く。描いたら PNG で端まで見る。
- **半角の文字（数字・`.`・`-`・空白・`§`）を含む行は、ノードや辺のラベルの一番長い行にしない。** `check_doc.py --render` の PNG では、半角の文字が測った幅より広く描かれ、一番長い行の右端が欠ける（「0.7以上」→「0.7以」、辺の「原文 §3」→「原文 §」。2026-10-02 の試験で2本とも起き、2026-10-05 に別の環境と手元の両方で再現した）。全角だけの行を一番長くするよう折る（「スコアが<br>0.7以上」「OCR経路へ<br>処理を戻す」）か、半角を減らす（「原文 §3」→「原文の3章」）。check_doc は該当するラベルを warning で知らせる。`--mermaid-init` の1行はノードの余白を広げ（`padding: 24`）SVG のラベル（`htmlLabels: false`）にしてあるが、これで消えるのは辺のラベルの欠けだけ。**箱のラベルは init では直らない。** 箱は PNG を見て、`<br>` で折るか短くする手当てが要る。
- **ラベルに章参照を書かない。** 図の中の「§6」は読み手に何も伝えず、描くと欠けやすい。ラベルは短い名詞にし、参照は図の下の文に書く（「等しいときの扱いは未決（§1.1）」）。check_doc は `mermaid-ref-label` で知らせる。
- **init の1行の中身。** 最上位の `fontFamily`（`themeVariables` の中だけでは描画の書体が既定の trebuchet ms のまま）と、辺のラベルの背景を不透明にする `themeCSS`（既定は半透明で、下の線が文字に透ける）を含む。どちらも Mermaid 11.16.1 で確かめた（2026-10-06）。古い版の1行は `mermaid-theme` で知らせる。
- **Mermaid の書き方**: 1行目は図の種類（`flowchart TB` / `flowchart LR` / `gantt`）。日本語のラベルは `["「保留」"]` のように引用符で囲む。改行は `<br>`。工程表は `:crit` で1本だけ色を変える。開始日が未定なら仮の日付と書く。VSCode のプレビューには拡張機能「Markdown Preview Mermaid Support」が要る。Notion のコードブロック（言語 mermaid）はそのまま図になる。
- **描いたら `check_doc.py --render` の PNG を Read で見る。** 文字の重なり、矢印の向き、ラベルの欠け、色の意味を確かめる。

## 書き方

- **原文の業務・要件は保持し、読み順と表現だけを変える。** 要件の削除・変更と、表現の変更を分けて本人に示す。要件を落として短くするのは目的ではないが、「冗長」と言われたら読む字数（文章＋表。図のラベルは数えない）を上限以下にする（原文と、原文の中身の1.5倍の小さい方。SKILL.md の表）。図を数えないのは、冗長でない原文（削れる量が2%）では上限が原文の長さそのものになり、図を1枚足すだけで超えたから。図は読む負荷が文章と違う。
- **状態の語を守り、原文の語を写す。** 参考値（「約1%」）を実績に、想定（「3か月」「1日20分」）を確約に、方針（「月次で調整する」）を実施済みに、提案を決定に変えない。逆に、原文の「実績」を参考値に下げたり、「必ず」を落としたりもしない。状態は方針を既定にし、ほかだけをその場に書く（「1日20分（想定）」「（決定）」）。表に「状態」の列は作らない（列を足すと全行に同じ語が並び、読む量だけが増える）。`claims.csv` の id は本文に見せず、`<!-- claims: C3 -->` に書く（id は読み手の道具ではなく、照合の道具）。
- **矛盾は両方残す。**「対象は PDF のみ」と「全請求書」が並ぶなら、どちらが実態かを確認する項目にする。AI が勝手に一つへ統一しない。統一したいなら 提案 として本人に採否を聞く。ただし矛盾と呼ぶのは、2つの記述が同時に成り立たないときだけ。今回の範囲（「第1工場は対象外」）と将来の検討（「試行の後に展開を検討する」）は両立するので、原文の語のまま両方を書く。
- **未決は §1 の「まだ決めていない点」の表（項目／決める担当／決め方）に1回だけ載せ、本文では「未決（§1.1）」と参照する。**「別マニュアル参照」「追って定める」で完成扱いにしない。決める担当と決め方が書けない未決は本人に尋ねる。尋ねられないときは、担当が原文に無ければ「原文に無い」、決め方が分からなければ空欄にする（全行が「本人に確認」の列は、読み手に何も伝えない）。
- **原文の条件と分岐の数を変えない。** 2つの条件を1つにまとめると意味が変わる（試験では「根拠の条文を示せる」と「類似度が閾値以上」を1つにした版があった）。2つの記述の関係が原文に無ければ、表の並びや図の矢印で順序を決めない（試験では「現地で確認」→「製造課が止めるかを決める」の矢印を引いた版があった）。
- **用語は使う場所で説明する。** 同じ語に複数の意味があるなら分ける（「保留」＝文字が読めない／確信度が低い／対象外の書類の疑い）。
- **数値には単位・母数・測定条件を添える。**「読み取り精度99%」は何のデータで、いつ、どの版で測るかが無いと警報にも合格条件にも使えない。
- **強い表現には前提を添える。**「致命的ではない」「全体は停止しない」には、キュー上限・保持期間・許容遅延などの条件を書く。
- **章参照は `§3.2` の形で、他の文書は文書名を前に（`基本設計 §5.1`）。** `check_doc.py` が本文にない章への参照を止める。

## 冗長さを削る

- **段落を4つに分けて、中身の無いものは丸ごと削る。** 残す（決定・条件・担当・数値・手順・例外・期限）／1か所にまとめる（繰り返し）／削る（一般論・心構え・前置き・言い訳）／未決にする（必要そうだが中身が無い）。手順は `SKILL.md` のフェーズ2.1。本題に関係ない素材を削ると理解が大きく上がり、見出しや強調を足す効果の約2倍だった（coherence 効果。slides の `references/evidence.md`）。
- **手順の段落は、一般論の語を含んでも削らない。** 「止まった期間の入力を再抽出して取り込みを再実行する必要がある」は、数字も固有名も無いが作業を書いている。候補に落とすと作業が消える（実際の運用設計で手順の段落が削除候補になった）。check_doc は「〜を〜する」の作業の文を block にせず `filler-action` で知らせるので、語（「必要がある」）だけ外すか、値・担当・頻度に置き換える。
- **削っても読む気は戻らない、は構造の問題。** 削除候補を0にしても読みにくければ、`check_doc.py --structure` で前置き・引く表の位置・章の型・未決の位置を見る（上の「読む路と引く表」）。
- **要約で縮めない。** 「〜の場合は〜し、〜なら〜する」を「適切に対応する」と縮めると、条件が消える。縮めるのは削除とまとめで行い、残す文は言い換えない。
- **一般論・心構えは書かない。** 「AI システムは導入して終わりではない」「関係者が密に連携することが重要である」は、どの設計書にも書けるので、この設計書の判断を何も伝えない。読み手は、中身のある段落を探して読み飛ばすことになる。
- **前置きは書かない。** 「本章では〜を説明する」は見出しと同じことを言っている。冒頭の「この文書が扱うこと」の表と、質問に答える見出しで足りる。
- **ヘッジと言い訳を重ねない。** 「〜と考えられる」「可能性がある」「ある程度」は、確かめていない箇所の水増しになる（verbosity compensation）。確かめていないなら 未決 にして、決める担当を書く。ヘッジだけの文を言い切りに直して残さない（「合格条件は必要に応じて見直す」→「合格条件は見直す」は、決まっていないことを決まったように見せる）。残す文の限定語（適宜・約・目安・原則）は外さない。
- **同じ内容は1か所だけに書く。** 文書内でも文書間でも、2か所に書くと片方だけ直されて意味がずれる（最初に適用した4文書では、判定規則が2通り・組織名が3通りに分かれていた）。正本の章に書き、ほかは「§4.2 を参照」「基本設計 §4.2 を参照」にする。
- **1段落1論点、全角200字以内。** 条件が3つ以上並ぶ文は表にする。章の文章が1000字を超えるなら、表・図へ移すか節に分ける。
- **削ったことを示す。** 削った段落の一覧（原文の行・4分類・理由）を本人に渡し、`check_doc.py --original` の読む字数・段落数・一般論の比較を添える。要件を落としていないことは、主張の表の doc / both の行が全部本文に出てくることで確かめる。
- **同じ事実は2か所まで。** 正本の章に全文、§1 の要点に1行と参照。対照表・流れの表・計画の表・図で同じ条件や数値を書き直さない。2026-10-02 の試験では、一般論を消した書き直しでも、合格条件が5か所、主張IDが最大8回出て、読む量が原文の約2.6倍になった。主張ID（C1）は正本で1回だけ添える。
- **同じ数値は2回まで。** 「300件」を8回書いた版があった。正本の章に1回、§1 に1回まで（`restated-number` が知らせる）。
- **原文に無い穴と案は設計書に足さず、報告に書く。** 気づいた穴をすべて「まだ決めていない点」に足すと、一覧が原文の何倍にもなり、原文の未決と区別できなくなる。読み手は報告を見られないので、本文には件数も書かない（`<!-- 報告に回した穴: N件 -->` のコメントにする）。案は「提案（未採択）」の章にだけ置き、図・運用の表に入れない（未採択の値を図に描いた版は、決まった手順と読まれる）。
- **表は3行以上のときだけ。** 2行の表は文より長くなる。全行が同じ値か空欄の列は消す（`same-column` が知らせる）。「現行と変更後」の表は、原文が置き換えを書いているときだけ作り、1行の中で単位をそろえる。
- **誰が何をするかは1か所にまとめる。** 原文に体制の表があれば、それを正本にして本文の同じ内容を吸収する。役割を図と文に散らすと、運用の担当者が1か所で読めない（試験で、体制の表をまとめた版が運用の担当者の点で上回った）。
- **条件・担当・期限を図の中だけに置かない。** 図のラベルは短い名詞にし、値と条件の全文は文か表に書く。矢印が1〜2本で済む図は文にする。
- **作業の経緯を本文にも付録にも書かない。** 「1か所にまとめた」「試験のため仮に決めた」は読み手の役に立たず、自己申告が実物と合わないこともある（試験で2本）。付録は「原文 §3 → §4.1」の対応だけにし、経緯と理由は報告に書く。

## 指摘の分け方

レビューで見つけた問題は4つに分けて書く。一般論を足して設計済みに見せない。

| 分類 | 例 | 誰が直すか |
|---|---|---|
| 編集で直せる | 不自然な表題、重複する一般論、参照先のずれ、誤記 | 改稿で直す |
| 別文書で補える | 指標の定義は精度検証にある | 参照に置き換える |
| 設計判断が必要 | 判定規則の統一、閾値を含む本番の設定の単位、警報と合格の分離 | 推奨を書き、本人が決める |
| 根拠を実測する必要がある | 現行の実測値、作業量、費用 | 未決にして担当と決め方を書く |
