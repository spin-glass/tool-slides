## 文書の役割分担（4文書の例）

- **基本設計**: 何を変えるか、誰から何を受け取り、どの結果を返すか。判定規則・データ契約の正本。
- **処理設計（ML設計など）**: どの処理・版・承認済みの設定で結果を作り、更新・復旧するか。
- **精度検証**: 何を正解とし、どのデータで測り、どう合否を決めるか。指標・合格基準の正本。
- **運用・移行**: 誰がいつ確認・対応し、どの条件で次へ進むか。定常作業・異常対応・移行判断。

共通事項の全文を4か所に複製しない。短い要点と、定義の正本・版への参照にする。文書の担当範囲が重なると、同じ用語・数値・判定条件の意味がずれる（最初に適用した4文書では判定規則が2通り、組織名が3通りあった）。

## 構成

- **冒頭1ページは「この文書で決めること／読む人／関連文書／原文／状態」の表。** 読者は自分が読むべき文書と節を最初の画面で知りたい。複数の文書で同じ「位置づけと読み方」を使い回すと、本文に無い章を指したままになる。
- **§1 は要点と判断事項: 解く問題、対象、提案の要点、今回決めたこと、まだ決めていない点。** 意思決定者は §1 だけ読む。未決を冒頭に出すと、確定した仕様として読まれない。
- **章の順は、要点 → 全体像（現行と変更後の対照）→ 日常の流れ → 判断基準と例外・変更 → 計画 → 体制と作業量 → 付録。** 具体的な利用場面 → 入力と出力 → 通常時と例外時の流れ → 重要な設計判断と理由、の順が読みやすい。14章に一般論が分散すると、現状・担当・判断条件がつながらない。
- **各章は、具体的な質問に答える見出し → 結論 → 図か表 → 詳細。**「明日アラートが出たら誰が何を判断するか」「次の段階へ進めるのはいつか」に答えられる単位で章を切る。
- **付録に用語、原文との対応、要件表のずれ、版管理の詳細を置く。** 本文は読み順、付録は参照用。原文の内容を落とさないために対応表を付ける。

## 図

- **章（`##`）の見出しの直後に図を1つ置き、本文はその説明にする。** 言葉だけより絵を添えた方が理解が上がる（multimedia principle）。注記は図のすぐ下に置く（spatial contiguity）。
- **目的で図の種類を選ぶ。** 関係は構成図（flowchart）、時間順は工程表（gantt）か処理フロー（flowchart LR）、差は比較表（Markdown の表）、抽象的な規則は具体例つきの図。表は拡張機能なしで表示できる。
- **図ごとに範囲を示し、矢印に意味を書く。** `-->|はい|` のようにラベルを付ける。何から何へ、どの条件で、が無い矢印は読み手が補うことになる（C4 の点検項目）。
- **1枚に全階層を詰めない。** 2段まで。3段目が要るなら、その枝だけ別の図にする。
- **ひし形のラベルは1行8字以内、ほかのラベルは1行12字以内。** ひし形は文字が欠けやすく、半角の `?`・`§`・空白は端で切れやすい（試験で2回起きた）。長い条件は `<br>` で折るか、条件を表に出してひし形には「条件を満たす？」とだけ書く。描いたら PNG で端まで見る。
- **Mermaid の書き方**: 1行目は図の種類（`flowchart TB` / `flowchart LR` / `gantt`）。日本語のラベルは `[「保留」]` のように角括弧で囲む。改行は `<br>`。強調は `classDef ai stroke:#d1495b` ＋ `class D2 ai`、工程表は `:crit` で1本だけ色を変える。開始日が未定なら仮の日付と書く。VSCode のプレビューには拡張機能「Markdown Preview Mermaid Support」が要る。Notion のコードブロック（言語 mermaid）はそのまま図になる。
- **描いたら `check_doc.py --render` の PNG を Read で見る。** 文字の重なり、矢印の向き、ラベルの欠け、色の意味（赤＝人の判断が要る、など）を確かめる。

## 書き方

- **原文の業務・要件は保持し、読み順と表現だけを変える。** 要件の削除・変更と、表現の変更を分けて本人に示す。要件を落として短くするのは目的ではないが、「冗長」と言われたら読む字数（文章＋表＋図のラベル）は原文より減らす（目安80%以下）。
- **状態の語を守る。** 参考値（「約1%」）を実績に、想定（「3か月」「1日20分」）を確約に、方針（「月次で調整する」）を実施済みに、提案を決定に変えない。状態は例外だけをその場に書き（「1日20分（想定）」）、方針・決定には付けない。表に「状態」の列は作らない（列を足すと全行に同じ語が並び、読む量だけが増える）。`claims.csv` の id は正本で1回だけ添える（例「（C3）」）。
- **矛盾は両方残す。**「対象は PDF のみ」と「全請求書」が並ぶなら、どちらが実態かを確認する項目にする。AI が勝手に一つへ統一しない。統一したいなら 提案 として本人に採否を聞く。
- **未決は `[要確認]` と書き、§1 の「まだ決めていない点」の表（項目／決める担当／決め方）に載せる。**「別マニュアル参照」「追って定める」で完成扱いにしない。決める担当と決め方が書けない未決は本人に尋ねる。尋ねられないときは、担当を「（仮）」付きで置き、決め方を「本人に確認」とする。
- **用語は使う場所で説明する。** 同じ語に複数の意味があるなら分ける（「保留」＝文字が読めない／確信度が低い／対象外の書類の疑い）。
- **数値には単位・母数・測定条件を添える。**「読み取り精度99%」は何のデータで、いつ、どの版で測るかが無いと警報にも合格条件にも使えない。
- **強い表現には前提を添える。**「致命的ではない」「全体は停止しない」には、キュー上限・保持期間・許容遅延などの条件を書く。
- **章参照は `§3.2` の形で、他の文書は文書名を前に（`基本設計 §5.1`）。** `check_doc.py` が本文にない章への参照を止める。

## 冗長さを削る

- **段落を4つに分けて、中身の無いものは丸ごと削る。** 残す（決定・条件・担当・数値・手順・例外・期限）／1か所にまとめる（繰り返し）／削る（一般論・心構え・前置き・言い訳）／未決にする（必要そうだが中身が無い）。手順は `SKILL.md` のフェーズ2.1。本題に関係ない素材を削ると理解が大きく上がり、見出しや強調を足す効果の約2倍だった（coherence 効果。slides の `references/evidence.md`）。
- **要約で縮めない。** 「〜の場合は〜し、〜なら〜する」を「適切に対応する」と縮めると、条件が消える。縮めるのは削除とまとめで行い、残す文は言い換えない。
- **一般論・心構えは書かない。** 「AI システムは導入して終わりではない」「関係者が密に連携することが重要である」は、どの設計書にも書けるので、この設計書の判断を何も伝えない。読み手は、中身のある段落を探して読み飛ばすことになる。
- **前置きは書かない。** 「本章では〜を説明する」は見出しと同じことを言っている。冒頭の「この文書で決めること」の表と、質問に答える見出しで足りる。
- **ヘッジと言い訳を重ねない。** 「〜と考えられる」「可能性がある」「ある程度」は、確かめていない箇所の水増しになる（verbosity compensation）。確かめていないなら 未決 にして、決める担当を書く。
- **同じ内容は1か所だけに書く。** 文書内でも文書間でも、2か所に書くと片方だけ直されて意味がずれる（最初に適用した4文書では、判定規則が2通り・組織名が3通りに分かれていた）。正本の章に書き、ほかは「§4.2 を参照」「基本設計 §4.2 を参照」にする。
- **1段落1論点、全角200字以内。** 条件が3つ以上並ぶ文は表にする。章の文章が1000字を超えるなら、表・図へ移すか節に分ける。
- **削ったことを示す。** 削った段落の一覧（原文の行・4分類・理由）を本人に渡し、`check_doc.py --original` の読む字数・段落数・一般論の比較を添える。要件を落としていないことは、主張の表の doc / both の行が全部本文に出てくることで確かめる。
- **同じ事実は2か所まで。** 正本の章に全文、§1 の要点に1行と参照。対照表・流れの表・計画の表・図で同じ条件や数値を書き直さない。2026-10-02 の試験では、一般論を消した書き直しでも、合格条件が5か所、主張IDが最大8回出て、読む量が原文の約2.6倍になった。主張ID（C1）は正本で1回だけ添える。
- **原文に無い穴は設計書に足さず、報告に書く。** 気づいた穴をすべて「まだ決めていない点」に足すと、一覧が原文の何倍にもなる。載せるのは原文の未決・矛盾・本人が採った追加だけ。
- **付録に削った理由を書かない。** 付録は「原文 §3 → §4.1」の対応だけ。理由は報告に書く。

## 指摘の分け方

レビューで見つけた問題は4つに分けて書く。一般論を足して設計済みに見せない。

| 分類 | 例 | 誰が直すか |
|---|---|---|
| 編集で直せる | 不自然な表題、重複する一般論、参照先のずれ、誤記 | 改稿で直す |
| 別文書で補える | 指標の定義は精度検証にある | 参照に置き換える |
| 設計判断が必要 | 判定規則の統一、閾値を含む本番の設定の単位、警報と合格の分離 | 推奨を書き、本人が決める |
| 根拠を実測する必要がある | 現行の実測値、作業量、費用 | 未決にして担当と決め方を書く |
