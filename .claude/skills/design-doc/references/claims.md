# 主張の表（claims.csv）

設計書と確認型スライドは、この表から作る。表が正本で、本文はこの表の id を参照する。
`scripts/claims.py` が列と状態を検査し、slides の `lint_slides.py` はスライドの `<!-- claims: C1,C2 -->` を、
`check_doc.py` は設計書のフォルダの表を検査する。

## 列（この順）

| 列 | 書くこと | 例 |
|---|---|---|
| id | 主張ID。英字で始まる英数字 | C1 |
| doc | 原文の文書名。本人の説明や会議なら出所 | 運用・移行設計／経理部の定例 2026-09-20 |
| section | 原文の章・箇所。版が複数なら版も | §6.1–6.4／40–44行 |
| claim | 主張を1文で。原文の言葉を保ち、数値は単位・母数つき | 試験1か月→並行1か月→切替1週→定常3週で移す |
| status | 下の7つ | 想定 |
| evidence | 根拠（測定・原文の引用・決めた人と日付）。事実・決定には必須 | 経理部長の決定（2026-09-20 の定例） |
| owner | 決める担当（未決・提案のとき） | 経理課長 |
| target | 掲載先: doc / deck / both / none | both |
| note | 補足。矛盾する別の記述、注意点 | 原文は「上回る」と「以上」が混在 |

任意の列（無くてもよい。既存の9列の表はそのまま通る）。出典がファイルなら書く。

| 列 | 書くこと | 例 |
|---|---|---|
| path | 出典のファイルのパス（`~` 可。相対パスは claims.csv のフォルダから）。本人の発言・会議なら空 | ~/docs/ops_design.md |
| rev | 出典を読んだときのコミット（短いハッシュ） | a1b2c3d |
| quote | 出典の該当文をそのまま写したもの。限定句を落とさない | 読み取り件数の面では夜間の一括処理で足りる。 |

`claims.py` は path があると出典と照らす: quote が今の出典に無い（quote-not-found）、rev の後に出典が変わった（source-changed。変わった回数と最初のコミットを出す）、path があって quote が無い（状態が事実・方針・想定・参考値・決定のとき）は block。出典に未コミットの変更がある（source-dirty）、quote の限定の語（の面では・限り・ただし・場合・前提・未決・見込み・想定・仮・目安・約・以上・未満・まで・だけ・のみ・暫定）が claim に無い（qualifier-dropped）は warning。
出典が変わったと出たら、出典を読み直して quote と claim を確かめ、rev を今のコミットにする。

## 状態の見分け方

| 状態 | 意味 | 原文の例 → 書き方 |
|---|---|---|
| 事実 | 測定・記録で確かめたこと、原文が「実績」と書いていること、原文が現状として述べること（「現在は週1回巡回している」）。evidence に原文の箇所か照合の方法を書く。集計元が原文に無ければ note に「集計元は原文に無い」と書き、状態は下げない | 「月約600件（2026年7月の実績）」→ 事実。本文も「実績」と書く |
| 参考値 | 原文が「目安」「約」「再集計する」と書く数値、または測定条件が残っていない数値 | 「約1%（目安であり再集計する）」→ 参考値。本文は「約1%（目安）」 |
| 方針 | 原文に「こうする」と書いてあること。実施済み・実績ではない。決めた人と日付が無い導入判断（ヘッジつきを含む）も 方針 | 「閾値は月次で評価・調整する」→ 方針 |
| 想定 | 見積り・仮の期間・仮の工数 | 「移行は3か月」「確認は1日20分」→ 想定。確約と書かない |
| 提案 | レビューで足した案。原文には無い。本人未採択なら note に書く | 「本番の設定に番号を付けて切り戻しの単位にする」→ 提案 |
| 決定 | 決めた人と日付がある決定。本人の原文を evidence に | 「決めた4点」→ 決定（経理部長、2026-09-20 の定例） |
| 未決 | まだ決まっていない。スライドでは `[要確認]{.tbd}` か「まだ決めていない点」の一覧に出す | 「保留」の上限の数値 → 未決（決める: 経理課長） |

限定句つきの文（「読み取り件数の面では夜間の一括処理で足りる」）は、限定句を claim に残す。限定の外側（「繁忙期に処理枠を確保できるか」）について原文が未決と書いていれば、それは別の行の 未決 にする。限定句を落とすと、未決の事柄まで決まったように読める。
状態は原文の語から決め、原文の語（実績・目安・想定・未実測・必ず・限り・以上／未満）は claim にそのまま写す。出所が疑わしくても上げ下げせず、note に書く。
状態を上げるとき（提案→決定、参考値→事実）は evidence に根拠を書き、黙って書き換えない。
決める担当（owner）が原文に無いときは「原文に無い」と書く。作業を進めるために具体的な担当を仮に置くなら note に「仮: 総務課長」と書き、報告で本人に確かめる（claims.py は未決・提案に担当が無いと warning を出す）。
設計書に載せず報告だけに回す主張（作業中に気づいた穴、採るか分からない案）は target を none にする（`claims-unused` の対象外になる）。
矛盾する2つの記述（例: 基本設計 §4.2 と精度検証 §5.3 の判定規則）は、1行にまとめて note に両方を残すか、2行にして互いを note で指す。

## 使われ方

- スライドの各枚: `<!-- claims: C3,C8 -->`。未決（status 未決）の id を載せた枚は、`[…]{.tbd}`・`::: {.undecided}`・「確認中」「未決」の語のどれかで未決と分かる形にする（lint が block する）。
- 設計書: 本文に id は見せない（読み手は claims.csv を見ない）。すべて、正本の段落か表の直後に `<!-- claims: C3,C8 -->` と書く（`check_doc.py` の `claims-unused` はこのコメントも数え、`claim-id-visible` は本文に見えている id を知らせる）。§1 の「まだ決めていない点」は 未決 の行から作る。
- 付録: スライドの付録に id・主張・出所・状態の表を、`claims.csv` を読むコードセルで出す（手で写さない）。
