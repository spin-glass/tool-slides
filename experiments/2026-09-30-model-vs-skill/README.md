# 検証: 出来はモデルによるのか、スキルによるのか

計画｜作成 2026-09-30｜この節（計画）は実行前に書いてコミットした。結果は末尾の「結果」に追記する。

## 問い

1. 画像で説明するデッキの出来は、モデル（Fable 5.1）によるのか、`slides` スキルによるのか。
2. 「具体例の画像で説明する」型の一般化は、スキルの作例に無い切り口でも効くか。

## 課題（スキルの作例に無い題材と切り口）

**誤分類を、実際の画像で説明するデッキ**を作らせる。牧場の動物6クラス（羊・ヤギ・アルパカ・鹿・牛・馬）、評価用240枚、誤り28枚。
スキルの作例と見本デッキは「閾値の移動（犬の外れ値）」だけで、「正解×予測」の切り口の作例はスキルに入れていない。
データは `prepare_data.py` で作った（Open Images V7、CLIP ViT-B/32 の zero-shot 分類）。

依頼文は全条件で同じ（`task/prompt_image.md`）。聴衆・行動・持ち時間（10分）を与え、構成は任せ、途中の承認は不要と伝える。
スキルありの条件だけ、先頭に `/slides ` を付ける。

補助の課題（ゲート）: 聴衆・行動・時間を与えない依頼（`task/prompt_gate.md`）に、質問で返すか、書き始めるかを見る。

## 条件

| 因子 | 水準 |
|---|---|
| モデル | Fable 5.1 / Opus 5.5（主）。Sonnet 5.5（副）。Haiku 4.5（ゲートのみ） |
| スキル | S0 なし / S1 初版（画像の仕組みが無い版、コミット 7b4428f） / S3 現行（一般化後、コミット 769927d） |

- 主比較: {Fable, Opus} × {S0, S3} を各2回（8回）。
- 副: {Fable, Opus} × S1 を各1回（スキルに画像の仕組みが無かったとき、モデルが自力で補えるか）。Sonnet × {S0, S3} を各1回。
- ゲート: 4モデル × {S0, S3（`/slides` なし）, S3（`/slides` あり）} を各1回。

そろえるもの:

- 作業場所はリポジトリの外に作る新しい Quarto プロジェクト（`run.py build`）。既存のデッキは置かない。S3 の SKILL.md からは見本デッキへの参照1行だけを除く。
- 共通の README・データ・テーマ・専用の venv。`claude -p`、`--effort high`、同じ許可ツール（Bash・Read・Write・Edit・Skill）。
- MCP（Notion 等）と、外へ出る道具（Artifact・Web・サブエージェント）は全条件で無効。
- 承認や確認を求めて止まった場合は、どの条件でも「承認します。このまま最後まで作ってください。」を最大2回返す。回数を記録する。

## 指標

スクリプトで測るもの（`score.py`。描画した HTML と qmd から）:

| 観点 | 指標 |
|---|---|
| 量 | 本編の枚数（10分の目安は6枚）、1枚あたり本文の文字数（平均・最大）、bullets（平均・最大）、ヘッジ・前置き語の数 |
| 型 | 結論を言い切るタイトルの割合、ノートの使用 |
| 正しさ | 描画できるか、数値の誤り（スライドの数値を `predictions.csv` と照合） |
| 過程 | 承認を返した回数、スキルを呼んだか、ターン数・時間・費用 |

条件を伏せた評価者（3モデル、デッキは無作為な記号と順番で渡す）が見るもの（`judge/rubric.md`）:

- 事実の確認: 誤った画像を何枚見せたか、選び方の記載、対比（正しい例・間違えた先の例）の有無、出典の記載、はみ出し・判読不能
- 5段階の評価: 聴衆に合う／どの画像で間違えるかが画像で分かる／タイトルだけで話が通る／量が10分に合い余計な説明が無い／見た目の破綻が無い／次にすることが分かる／総合

## 判定規則（実行前に固定）

1回の実行を次で「合格」とする: 描画できる ∧ 数値の誤り0 ∧ 本編7枚以下 ∧ 言い切りタイトル80%以上 ∧ 本文が最大250字以下 ∧ 誤った画像を20枚以上（28枚中）画像として見せる。

- **スキルのおかげ**: Fable・Opus とも S3 は合格し、S0 は不合格。
- **Fable のおかげ**: Fable は S0 でも合格し、Opus は S3 でも不合格。
- **両方**: Fable×S3 だけが合格。
- それ以外はそのまま報告する。同じ条件の2回で合否が割れたら「不安定」と書く。
- 一般化（問い2）: S3 の4回中3回以上が合格なら「作例に無い切り口でも効く」とする。S1 との差は参考として報告する（各1回）。

盲検評価は独立の確認に使う。総合点の条件間の差が0.5未満なら「差があるとは言えない」と書く。

## 追加の確認（手順確認の実行を見て、主条件の結果を見る前に追加）

手順確認のために走らせた Haiku × S3 のデッキは、型（タイトル・枚数・選び方の記載）は満たしたが、
画像の説明が実際の画像と合っていなかった（野生のヤギが岩場に小さく写った写真を「撮影角度と光の影響」と説明）。
型の合否だけでは、この違いが測れない。そこで次を追加する。合否の判定規則には入れず、別の表で報告する。

- **記述の正しさ**: 誤った28枚を組ごとに並べた参照図（`results/truth-errors.jpg`）を評価者に渡し、各デッキが
  「どんな画像か」について述べた内容を、参照図と照らして 支持される／支持されない に分けて数える。条件は伏せる。

## 追加の条件（Fable の1回目の結果を見た後に追加。探索的）

主課題の依頼文は聴衆・行動・持ち時間を与えている。これはスキルのゲートが聞き出す内容そのもので、
スキルなしの条件にも同じ情報を渡していることになる。実際の使い方では、スキルが無ければこの3点は渡らない。
そこで、3点を与えない依頼（ゲートと同じ文）を、スキルなしで最後まで作らせた場合も見る（`run.py run under <model> S0 1`）。
質問が返ってきたら主課題と同じ内容を答える。Fable はゲートの実行（8ターン以内）でデッキを作り切ったので、それを使う。
この条件は事前の判定規則に含めず、同じ指標と盲検評価を並べて報告する。

## 追加の取り決め（全実行の指標を見た後、盲検評価と記述の確認の結果を見る前に追加）

指標を出した時点で気づいた点を、評価者の結果を見る前に決めておく。

- **字数の測り方の偏り**: 本文の字数は描画した HTML の文字を数える。スキルなし・初版のデッキは画像の下の説明文を HTML で書き、
  現行スキルのデッキは図の中に描くので、同じ見た目でも前者だけ字数が増える。判定規則はそのまま当てはめ、
  あわせて「画像1枚ごとの説明文を除いた字数」（`chars_max_nocap`）で判定し直した結果も並べて報告する。
- **数値の誤りの数え方**: `predictions.csv` と `credits.csv` から計算できる数値と、デッキ内の合計の整合を対象にする。
  目視の分類に基づく枚数（「野生種は13枚」など）は対象外とし、記述の正しさの確認に任せる。結果は `results/number_errors.csv`。
- **参照図**: 記述の正しさの確認には、同じ28枚を大きく描き直した2枚（`results/truth-errors-1.jpg`、`-2.jpg`）を渡す。
  元の `truth-errors.jpg` は1枚あたり約80pxで、何が写っているかを確かめられないため。
- **評価者**: 盲検評価は3名（Opus 5.5・Fable 5.1・Sonnet 5.5 の新しいサブエージェント。提示順は各自別）。
  記述の確認は2名（Fable 5.1・Opus 5.5）。対象は15デッキ（主課題12、手順確認の Haiku 1、3点を与えない依頼 2）。
  渡す文面は `judge/prompt_judge.md`・`judge/prompt_factcheck.md`（`judge.py prompt` で組み立てる）。
- **「スキルなし」の範囲**: 無いのは `slides` スキルだけ。利用者の環境にある他のスキル（`dataviz` など）は全条件で有効で、
  スキルなしの4回（Fable 1回、Opus 3回）で `dataviz` が呼ばれた。

## 追試の計画（主課題の盲検評価を見た後、追試の実行前に書いた）

主課題の盲検評価（評価者1名は完了、2名は途中のメモ）では、スキルありのデッキがスキルなしより低く出た。
評価者が挙げた理由は3つに集まった。(1) 画像が小さい（1枚70〜100px。スキルの「1枚のスライドに48枚まで」の目安と
図の関数が原因）、(2) 結論の後に付録が区切りなく続く（appendix の印が画面に出ない）、(3) 何が写っているかを言い切らず、
見た目の特徴だけを書く（スキルの「見て分かった事実だけを書く」が効きすぎた）。
この3点を直した版を **S4** とし、直したことで差が埋まるかを確かめる。

- **S4 の変更**: 図の関数は、列数を省くと1枚が最も大きくなる並べ方を選ぶ。横長の写真には横長の枠。小さい群を詰めて並べる
  `flow_figure`、2行の説明文。`render_check.sh` が図ごとの1枚の大きさを表示する。目安を「1つの図に12〜16枚、1枚150px以上」に変更。
  appendix のスライドにはタイトルの上に「付録」と出す。「何が写っているかを言い切る」「本編の最後は依頼で終える」を規約に追加。
- **課題2（新しい課題）**: 同じ240枚を旧版（zero-shot）と新版（各クラス10枚の見本による few-shot）で判定した結果
  （`prepare_task2.py`、`task2/`）。正解率は 88% → 87% でほぼ同じだが、12枚が直り、16枚が新たに誤る。切り口は「変更の前後」で、
  スキルに作例は無い。依頼文は `task/prompt_change.md`（聴衆・行動・持ち時間10分を与える）。
- **条件**: 課題2で {Fable, Opus, Sonnet} × {S0, S4} を各1回（6回）。主課題で {Fable, Opus} × S4 を各1回（2回）。
- **評価**: 盲検の評価者3名（Opus・Fable・Sonnet、新しいサブエージェント）。課題2は6デッキ（`judge/rubric_change.md`）。
  主課題の S4 は、比べる相手として1回目の S0・S3 の4デッキを混ぜた6デッキ（`judge/rubric.md`）。記述の確認は課題2だけ、2名。
  評価者が途中で止まるのを避けるため、メモは追記だけにし、最後の見直しは画像を開き直さずメモで行うよう文面を変える。
- **読み方（実行前に固定）**: 主な指標は盲検の総合点（3名の平均）。モデルごとに S4 と S0 を比べ、差が0.5未満なら「並んだ」、
  S4 が0.5以上低ければ「まだ下げている」、0.5以上高ければ「上げた」とする。画像の点（`images`）も同じ読み方で報告する。
  型の合否は主課題と同じ規則（字数は説明文を除いて数える。画像は、正誤が変わった28枚のうち20枚以上を見せる）で、参考として報告する。
- **限界**: S4 の3点は主課題の評価者の指摘から作ったので、主課題での S4 は「指摘が直ったか」の確認にすぎない。
  課題2は題材（牧場の動物・同じ240枚）が主課題と共通で、完全に独立な課題ではない。各条件1回。

## あらかじめ分かっている限界

- 合格の基準（枚数・文字数・タイトル）はスキルの規約そのもので、スキルありが有利になる。盲検評価は規約を知らされない評価者の判断で、これを補う。
- 各条件1〜2回で、検定はしない。小さな差は読み取れない。
- 1回の依頼で完結する実行で、対話しながら直す実際の使い方とは違う。effort は high で、先のデッキを作ったセッション（max）とは違う。
- S3 のスキルは、Fable が作ったデッキから書き起こしたもの。「スキルの効果」には Fable の過去の仕事が含まれる。
- 評価者も Claude のモデル。条件は伏せるが、文体への好みは残りうる。

## 結果

記入 2026-09-30｜集計の全体は `results/summary.md`、デッキは公開サイトの
[検証の一覧](https://tool-slides.toshihiro-engineer.workers.dev/experiments/2026-09-30-model-vs-skill/)（条件・型・評価の点つき）。

### 結論

1. **Fable だからではない。** 聴衆・行動・持ち時間を依頼文で渡すと、スキルなしでも Fable・Opus・Sonnet のデッキはどれも
   盲検評価の総合が 5.0（評価者2名の平均、5点満点）だった。画像の説明の誤りも、3モデルともほぼ無い（1デッキあたり0〜0.5件）。
2. **スキルが確実に効いたのは、中身ではなく入口と型。**
   - 入口: 聴衆・行動・時間の無い依頼に、スキルなしの4モデルは質問せずに作り始めた。スキルありは4モデルとも質問して止まった。
     3点なしで最後まで作らせたデッキは 2.5（Fable）と 3.5（Opus）で、3点を与えたときの 5.0 より低い。
   - 型: 事前の合否（枚数・タイトル・字数・数値・画像の枚数）は、スキルあり（検証時の版と改訂版。Haiku を除く）が10回中10回合格、
     スキルなしが8回中1回合格。
3. **検証時の版（画像の作り方を一般化した版）は、型をそろえる一方で、評価を下げた。** 主課題の総合はスキルなし 5.0 に対して 3.8〜4.0。
   評価者の指摘は3つにまとまった: 画像が小さい（1枚70〜100px）、結論の後に付録が区切りなく続く、何が写っているかを言い切らない。
4. **指摘を直した改訂版（S4）は、スキルなしと並んだ。** 主課題の作り直しは Fable・Opus とも 5.0（評価者1名。同じ評価者の採点で、
   スキルなし 5.0・検証時の版 4.0）。作例の無い新しい課題（変更の前後）では、総合が改訂版 対 なしで Fable 4.0 対 4.0、
   Opus 4.5 対 4.5、Sonnet 4.5 対 4.0。ただし画像の点は3モデルとも 4.5 対 5.0 で、まだ少し低い。また改訂版のデッキには、
   写真と合わない記述が3件あった（Fable 1件・Sonnet 2件。例: エンジンルームにヤギが写る車の写真を「動物が写っていない」）。
   スキルなしの3本は0件。
5. **スキルは中身の正しさを補わない。** Haiku はスキルありでも、画像の説明の中心が誤っていた
   （岩場の野生のヤギを「撮影角度と光の影響」と説明）。

### 事前の判定規則の当てはめ

- 主課題の合否: Fable×なし 1/2（2回目は本文310字で不合格）、Fable×検証時の版 2/2、Opus×なし 0/2、Opus×検証時の版 2/2。
  規則の3つの結論（スキルのおかげ／Fable のおかげ／両方）のどれにも当てはまらない。Opus は「スキルがあると合格」、
  Fable はスキルなしの2回で合否が割れた（不安定）。
- 問い2（一般化）: 検証時の版の4回中4回が合格なので、規則では「作例に無い切り口でも効く」。ただしこれは型の合否で、
  盲検評価（独立の確認）では総合がスキルなしより0.5以上低く、型の合否と逆の向きだった。
- 追試（実行前に固定した読み方）: 総合は Fable・Opus が「並んだ」、Sonnet が「上げた」（差0.5）。画像の点は3モデルとも
  「まだ下げている」（差0.5）。型の合否は改訂版 3/3、スキルなし 0/3。
- 数値の誤りは、全23デッキで0（`results/number_errors.csv`）。
- 費用と時間（1回）: Fable $1.8〜5.4・3〜12分、Opus $2.1〜2.8・9〜16分、Sonnet $1.1〜2.1・7〜11分。

### 計画から変えたこと

- Fable の週の使用枠が94%に達したため（17:40頃）、評価に Fable を使うのをやめた。主課題の Fable の評価者2名
  （盲検1名・記述の確認1名）は止め、書き終えていた15デッキ分の採点メモを使った。盲検の評価者の最後の見直しは
  15デッキ中10デッキで止まっていて、見直しで変えた点（3か所。総合点の変更は無い）は反映した。
- 主課題の Sonnet の評価者は、90分で15デッキ中8デッキ分のメモしか残らず（書き直すたびに消えていた）止め、集計に使っていない。
  主課題の盲検評価は2名（Opus・Fable）、記述の確認は2名（Fable・Opus）。
- 追試の評価は、計画の3名（Opus・Fable・Sonnet）を、変更の前後の課題で2名（Opus・Sonnet）、主課題の作り直しで1名（Opus）にした。
  記述の確認は1名（Opus）。5時間の使用枠（79%）に収めるため。評価者への指示に「メモは追記だけ」「最後の見直しは画像を開き直さない」を足した。

### 限界（あらかじめの限界に加えて）

- 評価者は1〜2名で、0.5点の差は評価者1名の1段階の違いで生じる。追試は各条件1回。
- 改訂版は1回目の評価者の指摘を見て作った。主課題の作り直しの点は「指摘が直ったか」の確認にとどまる。変更の前後の課題も同じ240枚の写真を使う。
- 並列の実行が `/tmp` の同じ名前のフォルダ（`/tmp/fe`・`/tmp/fc` など）を作業に使っていて、互いのファイルを読んだ可能性がある。
- 「スキルなし」でも利用者の環境の他のスキルは使えた。スキルなしの実行6回で `dataviz` が呼ばれた。
- 数値の誤りは、データから計算できる数値と合計の整合だけを数えた。目視の分類の数は、記述の確認で見た。

### スキルへの反映と、次の候補

- 反映済み（改訂版、コミット 4bf36be）: 1つの図は12〜16枚・1枚150px以上、列数の自動選択、横長の枠、`flow_figure`、2行の説明文、
  `render_check.sh` の大きさ表示、付録の印、「何が写っているかを言い切る」「本編の最後は依頼で終える」。
- 次の候補（未実施・未検証）: 言い切るのは写真で確かめたことだけにする（写真と合わない記述が3件出たため）。
  画像の点の差（4.5 対 5.0）は、少数を大きく見せる枚を増やすと埋まるかもしれない。

### 画像と主張の照合（本人の依頼で追加）
